## 2. Objetivo da Task
Criar as duas DocTypes canônicas descritas em arquivo (ADR-0002) no módulo `Locacao Automation`, com os controllers que impõem unicidade da ativa por provedor e a trava estrutural do carimbo de teste de conexão.

---

## 3. Descrição Detalhada
Criar as DocTypes **versionadas em JSON** (ADR-0002) sob `locacao_automation/locacao_automation/doctype/` — módulo `Locacao Automation`, que pertence ao app (o módulo `Locação de imóveis` das DocTypes legadas pertence ao erpnext e não é versionável aqui):

- `configuracao_integracao_bancaria/` — JSON com os campos da §7.2 (provedor, ativo, ambiente, auth_url, api_base_url, client_id, scope, certificado_arquivo Attach, certificado_senha Password, campos read-only de metadados, numero_cliente/conta/modalidade Int, parametros_provedor Long Text, ultimo_sequencial_seu_numero, pfx_path_legado, `conexao_testada_em`, `conexao_testada_hash`). Permissão `read/write/create` só a System Manager. Controller `validate()`: impõe **no máximo uma ativa por provedor**; ao detectar alteração em campo componente da conexão, **limpa** `conexao_testada_em`/`conexao_testada_hash` (trava de RN-04).
- `auditoria_configuracao_bancaria/` — JSON da §7.2 (configuracao Link, acao Select, autor, data_hora, impressao_digital_anterior/_nova, campos_alterados, resultado, mensagem). Somente-leitura: sem permissão de delete no controller.

DocTypes declarativas — a lógica testável vive nos controllers `.py`.

### 6.6 Detalhamento dos Casos de Teste

#### CT-100 — Salvar única configuração ativa por provedor é aceito
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: Uma única Configuracao Integracao Bancaria com ativo=1 para um provedor é sempre aceita pelo validate() do controller.
- **Pré-condições**: Nenhuma Configuracao Integracao Bancaria Sicoob previamente cadastrada no site de teste
- **Entrada**: {"descricao": "Documento com campos mínimos válidos para Sicoob", "valores": {"provedor": "Sicoob", "ativo": 1, "ambiente": "Producao", "auth_url": "https://auth.sicoob.com.br/token", "api_base_url": "https://api.sicoob.com.br/cobranca-bancaria/v3", "client_id": "cli-123", "numero_cliente": 1, "numero_conta_corrente": 1, "codigo_modalidade": 1}}
- **Passos**: Instanciar frappe.get_doc({'doctype': 'Configuracao Integracao Bancaria', ...campos válidos, ativo:1}); Chamar doc.insert(ignore_permissions=True); Consultar frappe.db.count('Configuracao Integracao Bancaria', {'provedor':'Sicoob','ativo':1})
- **Esperado**: "insert() completa sem exceção; frappe.db.count(...) == 1 imediatamente após o insert."
- **Negative companion**: CT-101 — segunda Configuracao Integracao Bancaria com ativo=1 para o mesmo provedor, enquanto a primeira permanece ativa → insert()/save() da segunda lança frappe.ValidationError e frappe.db.count(..., {'ativo':1,'provedor':'Sicoob'}) permanece 1
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-101 — Segunda configuração ativa para o mesmo provedor é recusada pelo validate()
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: No máximo uma Configuracao Integracao Bancaria ativa por provedor; tentar ativar uma segunda com uma já ativa existente falha e não altera a primeira.
- **Pré-condições**: doc1 (Sicoob, ativo=1) já inserido no setUp deste teste
- **Entrada**: {"descricao": "doc2 com mesmo provedor e ativo=1, campos válidos distintos de doc1 (client_id diferente)", "valores": {"provedor": "Sicoob", "ativo": 1, "client_id": "cli-456"}}
- **Passos**: Inserir doc1 (Sicoob, ativo=1) via insert(ignore_permissions=True); Montar doc2 (Sicoob, ativo=1) com campos válidos distintos; Chamar doc2.insert(ignore_permissions=True) dentro de assertRaises; Consultar frappe.db.count('Configuracao Integracao Bancaria', {'provedor':'Sicoob','ativo':1}) após a exceção
- **Esperado**: "doc2.insert() lança frappe.ValidationError; frappe.db.count(..., {'ativo':1,'provedor':'Sicoob'}) permanece 1 (doc2 não persistido; doc1 intocado)."
- **Negative companion**: self — este é o caso negativo (ver CT-100 para o positivo) → ver resultado_esperado
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-102 — Editar a própria configuração ativa não dispara falso positivo de duplicidade
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: A verificação de unicidade exclui o próprio documento (por name) da contagem de ativos concorrentes.
- **Pré-condições**: doc1 (Sicoob, ativo=1) já inserido
- **Entrada**: {"descricao": "Reabrir o mesmo doc1 e alterar campo não relacionado à unicidade", "valores": {"scope": "boleto_alterado"}}
- **Passos**: frappe.get_doc('Configuracao Integracao Bancaria', doc1.name); Alterar doc.scope mantendo ativo=1 e provedor=Sicoob (mesmo name); Chamar doc.save(); Consultar frappe.db.count(..., {'ativo':1,'provedor':'Sicoob'})
- **Esperado**: "save() completa sem exceção; frappe.db.count(..., {'ativo':1,'provedor':'Sicoob'}) == 1 (é o mesmo registro atualizado, não duplicado)."
- **Negative companion**: CT-101 — documento diferente (name distinto) tentando ativo=1 para o mesmo provedor → ver CT-101 — ValidationError e contagem de ativos permanece 1; aqui, ao contrário, o mesmo name deve ser aceito
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-103 — Carimbo de teste de conexão permanece intacto quando campo não-componente muda
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: Editar um campo que NÃO compõe a conexão (ex.: parametros_provedor) não invalida conexao_testada_em/conexao_testada_hash já preenchidos.
- **Pré-condições**: Registro pendente (ativo=0) com conexao_testada_em e conexao_testada_hash preenchidos, hash calculado pela mesma função interna do controller sobre os campos de conexão atuais
- **Entrada**: {"descricao": "Alterar parametros_provedor (campo não-componente da conexão)", "valores": {"parametros_provedor": "{\"x\": 1}"}}
- **Passos**: Criar/gravar o registro pendente com carimbo já preenchido (via fluxo real de teste de conexão simulado ou setUp equivalente); Alterar apenas parametros_provedor; Chamar doc.save(); Reler conexao_testada_em e conexao_testada_hash
- **Nota (decisão do dono da spec, 2026-07-21)**: `codigo_modalidade` deixou de ser não-componente — a trava RN-04 usa a CONTA COMPLETA (tripla ContaBancaria). O campo não-componente exercitado passou a ser `parametros_provedor`.
- **Esperado**: "Após save(), conexao_testada_em e conexao_testada_hash permanecem EXATAMENTE iguais aos valores gravados antes da alteração (comparação de igualdade estrita)."
- **Negative companion**: CT-104 — alteração de um campo que COMPÕE a conexão (auth_url, api_base_url, client_id, scope, conta ou impressão digital do certificado) → conexao_testada_em e conexao_testada_hash tornam-se None após o save()
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-104 — Carimbo é invalidado quando qualquer campo componente da conexão muda (parametrizado)
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: Alterar qualquer campo que compõe a conexão (auth_url, api_base_url, client_id, scope, conta, impressão digital do certificado) após o teste limpa conexao_testada_em e conexao_testada_hash — trava estrutural de RN-04.
- **Pré-condições**: Registro pendente com carimbo válido preenchido (mesmo setup de CT-103), repetido a cada sub-caso parametrizado
- **Entrada**: {"descricao": "Tabela de 8 sub-casos, um campo componente alterado por vez (CONTA COMPLETA — decisão do dono da spec)", "valores": {"campos_parametrizados": ["auth_url", "api_base_url", "client_id", "scope", "numero_cliente", "numero_conta_corrente", "codigo_modalidade", "certificado_impressao_digital"]}}
- **Passos**: Para cada campo da tabela: recriar o registro pendente com carimbo válido; Alterar SOMENTE aquele campo (reenvio de certificado simulado altera a impressão digital); Chamar doc.save(); Reler conexao_testada_em e conexao_testada_hash
- **Esperado**: "Para cada um dos 8 sub-casos: após save(), conexao_testada_em é None E conexao_testada_hash é None."
- **Negative companion**: self — este é o caso negativo (ver CT-103 para o positivo) → ver resultado_esperado
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-105 — Registro de auditoria é criado e lido normalmente
- **Tipo/Camada**: INTEGRACAO · service-integration · CA —
- **Invariante**: Um registro de Auditoria Configuracao Bancaria pode ser inserido e relido sem bloqueio — a restrição é exclusiva de delete.
- **Pré-condições**: Configuracao Integracao Bancaria válida existente para servir de Link
- **Entrada**: {"descricao": "Registro de auditoria mínimo válido", "valores": {"acao": "configuracao_alterada", "autor": "Administrator", "resultado": "sucesso", "campos_alterados": "scope"}}
- **Passos**: frappe.get_doc({'doctype':'Auditoria Configuracao Bancaria', ...}).insert(ignore_permissions=True); frappe.get_doc('Auditoria Configuracao Bancaria', doc.name)
- **Esperado**: "insert() sem exceção; frappe.db.exists('Auditoria Configuracao Bancaria', doc.name) é True; campos relidos batem com os gravados."
- **Negative companion**: CT-106 — tentativa de deletar o mesmo registro de auditoria → delete() lança exceção e o registro permanece em frappe.db.exists(...)
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-106 — Registro de auditoria não pode ser deletado (somente-leitura)
- **Tipo/Camada**: SEGURANCA · service-integration · CA —
- **Invariante**: O controller de Auditoria Configuracao Bancaria bloqueia delete estruturalmente, independente da permissão de DocType do usuário.
- **Pré-condições**: Registro de auditoria já inserido (mesmo do CT-105)
- **Entrada**: {"descricao": "Tentativa de exclusão via API do doc", "valores": {}}
- **Passos**: Reobter o doc de auditoria; Chamar doc.delete() (ou frappe.delete_doc(..., ignore_permissions=True) para garantir que o bloqueio vem do controller e não da camada de permissão padrão) dentro de assertRaises; Verificar frappe.db.exists('Auditoria Configuracao Bancaria', doc.name) após a tentativa
- **Esperado**: "delete() lança frappe.ValidationError (ou frappe.PermissionError, conforme implementação de on_trash); frappe.db.exists(...) continua True após a tentativa."
- **Negative companion**: self — este é o caso negativo (ver CT-105 para o positivo) → ver resultado_esperado
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)
