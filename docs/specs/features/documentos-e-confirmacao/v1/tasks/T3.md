## 2. Objetivo da Task

Mover o **esquema** para o estado que as duas frentes exigem, numa passagem só, porque o
`drizzle-kit` gera **uma** migração a partir do diff do esquema e porque o `DROP COLUMN` quebra a
compilação de quatro pacotes ao mesmo tempo.

Três mudanças de esquema:

1. **`negocio.contrato` perde `pdf_contrato_arquivo`** — some do que se guarda **e** do que se
   publica (CA-07, US-05). É a **única mudança incompatível deliberada** do produto até aqui.
2. **`negocio.locatario` ganha `email_confirmado_em`** — anulável, **só nesta tabela**. É o **fato**;
   o estado publicado é derivado dele (ADR-0022).
3. **`negocio.portador_de_confirmacao` nasce** — com `empresa_id`, RLS habilitada e **forçada**, FK
   composta e `UNIQUE` global sobre o derivado; mais a função `SECURITY DEFINER` que a resolve.

⚠️ **Esta task não escreve uma linha de aplicação da confirmação nem do documento.** Ela entrega o
substrato, e o preço dela é o raio: **22 arquivos**, medidos, e a maior parte é edição mecânica de
fixture.

## 3. Descrição Detalhada

### 3.1 `packages/db/src/esquema/negocio.ts`

- **Remove** `pdfContratoArquivo` da tabela `contrato`.
- **Acrescenta** `emailConfirmadoEm: timestamp('email_confirmado_em', { withTimezone: true })` **só**
  em `locatario` — locador e fiador não a ganham.
- **Cria** `portador_de_confirmacao`, conforme §7.2 do tech spec:

| Coluna | Tipo | Constraints |
|---|---|---|
| `id` | `uuid` | `PRIMARY KEY DEFAULT gen_random_uuid()` |
| `empresa_id` | `uuid` | `NOT NULL REFERENCES identidade.empresa(id)` |
| `locatario_id` | `uuid` | `NOT NULL`, **FK composta** `(locatario_id, empresa_id) → locatario(id, empresa_id)` |
| `derivado` | `text` | `NOT NULL`, **`UNIQUE`** — índice único; é por ele que a resolução busca |
| `expira_em` | `timestamptz` | `NOT NULL` |
| `consumido_em` | `timestamptz` | anulável — o portador consumido **permanece** (RN-10) |
| `invalidado_em` | `timestamptz` | anulável — o reenvio marca os anteriores (RN-09) |
| `criado_em` | `timestamptz` | `NOT NULL DEFAULT now()` |
| — | — | `UNIQUE (id, empresa_id)` — a forma canônica de referência tenantizada |

> **`derivado` é `UNIQUE` global, e não por empresa** — deliberado. A resolução acontece **antes** de
> existir contexto de tenant; unicidade por empresa admitiria colisão que a função `SECURITY DEFINER`
> teria de desempatar, e o desempate só poderia vir do pedido — exatamente o que a ADR-0024 proíbe.
>
> **Não há coluna do segredo em claro.** A ausência é a decisão (CA-14).

### 3.2 `packages/db/migracoes/0013_dominio_documentos_e_confirmacao.sql` — **gerada**

Gerada por `drizzle-kit` a partir do esquema acima: `CREATE TABLE negocio.portador_de_confirmacao`
(com `ENABLE ROW LEVEL SECURITY`), `ALTER TABLE negocio.locatario ADD COLUMN email_confirmado_em` e
`ALTER TABLE negocio.contrato DROP COLUMN pdf_contrato_arquivo`.

⚠️ **A `0007` NÃO é emendada** (decisão D4 do tech-alignment). O `migrar-banco.sh` registra
`sha256sum` por arquivo aplicado e **aborta** quando um arquivo já aplicado muda. Arquivo novo é
correto nos **dois** estados possíveis do banco.

### 3.3 `packages/db/migracoes/0014_seguranca_confirmacao.sql` — **autoral**

`FORCE ROW LEVEL SECURITY` + política `FOR ALL` na tabela nova, com `USING` e `WITH CHECK` na
**mesma expressão literal** das cinco migrações de segurança anteriores; e a função:

```sql
CREATE FUNCTION "negocio"."resolver_portador_de_confirmacao"(p_derivado text)
	RETURNS TABLE (empresa_id uuid, locatario_id uuid, consumido_em timestamptz)
	LANGUAGE sql
	STABLE
	SECURITY DEFINER
	SET search_path = pg_catalog, pg_temp
AS $$
	SELECT p.empresa_id, p.locatario_id, p.consumido_em
	FROM negocio.portador_de_confirmacao p
	WHERE p.derivado = p_derivado
	  AND p.invalidado_em IS NULL
	  AND p.expira_em > pg_catalog.now();
$$;
```

> ### ⚠️ `AND p.consumido_em IS NULL` **NÃO** entra neste `WHERE`
>
> A linha pareceria endurecimento e **quebraria a RN-10**: a reapresentação dentro da validade
> passaria a receber `404`, e a pré-visualização de link pelo provedor de e-mail queimaria a
> confirmação antes de o locatário clicar. A leitura conjunta ADR-0027 × RN-10 está registrada por
> escrito na **§21.3 do tech spec** — *"uso único é o EFEITO, não a RESOLUÇÃO"* —, e a unicidade é
> imposta pelo `UPDATE … WHERE consumido_em IS NULL RETURNING` (T11), nunca por filtro aqui.

As outras três propriedades, e cada uma é conteúdo: **não aceita `empresa_id` por parâmetro**
(ADR-0024); devolve **três colunas e nenhuma a mais**; o prazo e a invalidação estão no `WHERE`, de
modo que vencido e invalidado produzem **zero linhas**, indistinguíveis de inexistente — a RN-14 vira
propriedade do banco. E `pg_catalog.now()`, nunca relógio de processo (ADR-0026); por ser
`timestamptz`, **nenhum literal de fuso** é necessário — o que evita agravar o **D14 (F3/T5)**.

**Sem descida (`down`)** — é a convenção das cinco migrações de segurança anteriores.

### 6.6 Detalhamento dos Casos de Teste

#### CT-711 — Contrato sem imóvel é irrepresentável — a impossibilidade é do banco, não de validação de aplicação

- **Tipo**: INTEGRACAO | **Categoria**: integridade_dados
- **Arquivo**: `packages/db/test/contrato.spec.ts` (modificar)
- **Invariant**: É estruturalmente impossível gravar uma linha em `negocio.contrato` com `imovel_id`
  nulo — a coluna é `NOT NULL` e não existe caminho de escrita nesta porta que a omita — de modo que a
  recusa *"ValidationError: O Contrato nao possui imovel vinculado"* do legado não tem equivalente
  porque o estado que ela recusava não existe.
- **Owning layer**: `service-integration` | **Real execution boundary**: `db`
- **Pré-condições**:
  - instância efêmera de banco migrada até a migração corrente
- **Dados de entrada**: tentativa de `INSERT` com `imovel_id` nulo
  - `imovel_id`: `null`
- **Passos**:
  1. Sob o contexto de uma empresa válida, tentar
     `INSERT INTO negocio.contrato (…, imovel_id, …) VALUES (…, NULL, …)` direto pelo executor de
     transação
  2. Capturar o erro
- **Resultado esperado**: A instrução rejeita com **SQLSTATE 23502** (`not_null_violation`) nomeando a
  coluna `imovel_id` — nunca insere a linha.
- **Negative companion**: este é o caso negativo (`ct_id: self`) — entrada: `INSERT` direto em
  `negocio.contrato` com `imovel_id = NULL`, contornando a porta de aplicação, direto no banco
  efêmero; asserção: o banco recusa com erro de `NOT NULL` (23502) — nunca aceita a linha.
- **Critérios validados**: CA-06
- **Obs**: Registra, por prova executável, que `contrato_sem_imovel` é irrepresentável no produto — a
  divergência declarada (**DV-06**) não é uma recusa aplicada e sim **ausência estrutural do estado**,
  conforme RN-04 e CA-06.

#### CT-712 — A coluna `pdf_contrato_arquivo` não existe mais no catálogo depois da migração `0013`

- **Tipo**: INTEGRACAO | **Categoria**: integridade_dados
- **Arquivo**: `packages/db/test/contrato.spec.ts` (modificar)
- **Invariant**: Depois de aplicada a migração que remove `pdf_contrato_arquivo`, o catálogo do
  PostgreSQL (`information_schema.columns`) não lista essa coluna para `negocio.contrato` — a ausência
  é medida por introspecção, nunca presumida do texto da migração.
- **Owning layer**: `service-integration` | **Real execution boundary**: `db`
- **Pré-condições**:
  - instância efêmera de banco migrada até a `0013` (inclusive)
- **Dados de entrada**: consulta ao catálogo por colunas de `negocio.contrato`
- **Passos**:
  1. `SELECT column_name FROM information_schema.columns WHERE table_schema='negocio' AND table_name='contrato'`
  2. Verificar que `'pdf_contrato_arquivo'` não está no conjunto
  3. **PROVA DE FALSIFICAÇÃO**: rodar a mesma consulta contra uma instância **não** migrada até a
     `0013` (só até a `0012`) e demonstrar que a asserção de ausência **reprova** (a coluna aparece)
- **Resultado esperado**: Pós-`0013`: o conjunto de colunas não contém `'pdf_contrato_arquivo'`
  (afirmado por `.not.toContain`, não por comprimento). Pré-`0013` (controle): a coluna aparece, e a
  mesma asserção reprova — provando que ela detectaria a regressão.
- **Negative companion**: este é o caso negativo (`ct_id: self`) — entrada: **prova de falsificação**,
  reintroduzir a coluna (mutante que não aplica a `0013` ou a reverte) contra o **mesmo** teste;
  asserção: com a coluna presente, a asserção de ausência reprova nomeando `'pdf_contrato_arquivo'`
  encontrada — prova que a asserção detecta o defeito se ele voltar.
- **Critérios validados**: CA-07
- **Obs**: É a **métrica nº 2 do PRD** (*"ausência de qualquer documento armazenado"*) na sua ponta de
  banco. No molde do `CT-430` (ausência de `retirado_em` em `contrato_fiador`). ⚠️ Uma das **três
  provas de falsificação obrigatórias** desta sub-fatia.

#### CT-713 — O contrato publicado não aceita nem devolve `pdfContratoArquivo` — mudança incompatível deliberada

- **Tipo**: UNITARIO | **Categoria**: teste_negativo
- **Arquivo**: `packages/contracts/test/esquemas.spec.ts` (modificar)
- **Invariant**: `esquemaDeContratoNovo` recusa um corpo que traga a chave `pdfContratoArquivo` (chave
  desconhecida, `strictObject`), e `esquemaDoContrato` — a forma de saída — não declara essa chave em
  sua superfície de tipo.
- **Owning layer**: `unit` | **Real execution boundary**: `none`
- **Pré-condições**:
  - nenhuma
- **Dados de entrada**: corpo de contrato válido em todos os outros campos, mais a chave
  `pdfContratoArquivo`
  - `pdfContratoArquivo`: `"/frappe/private/files/contrato.pdf"`
- **Passos**:
  1. Montar um corpo de `ContratoNovo` válido acrescido de `pdfContratoArquivo`
  2. `safeParse` contra `esquemaDeContratoNovo`
  3. Verificar que a superfície de tipo `Contrato` (`esquemaDoContrato`) não expõe a chave
- **Resultado esperado**: `safeParse.success` é `false`; o issue nomeia `'pdfContratoArquivo'` como
  chave desconhecida (`unrecognized_keys`) — CA-07 provado na ponta do contrato publicado.
- **Negative companion**: este é o caso negativo (`ct_id: self`) — entrada: corpo de
  criação/alteração de contrato com `{ …, pdfContratoArquivo: '/algum/caminho.pdf' }`; asserção:
  `esquemaDeContratoNovo.safeParse(corpo).success === false`, com issues contendo um item de código
  `unrecognized_keys` apontando `pdfContratoArquivo`.
- **Critérios validados**: CA-07
- **Obs**: Complementa o CT-712 (banco) e o CT-714 (rota, em **T7**) — as **três** superfícies que a
  decisão D4 nomeia (migração, camada de dados, contrato publicado) ficam cada uma com prova própria.

## 7. Notas / Observações

- **Esta é a task de maior raio da sub-fatia, e o raio é declarado de propósito.** O tech spec §3.6.1
  nasceu de um achado do challenge — a spec declarava 10 arquivos e a medição encontrou 22.
- **A `0013` é destrutiva e NÃO tem descida.** Reverter o esquema exige **restauração de backup**, que
  é o item 1 da F7 e **ainda não está entregue**. Aplicar a `0013` a banco durável é ato sem volta
  enquanto a F7 não fechar (§16.6). Isso não bloqueia o run — a suíte roda em instância efêmera —, mas
  precisa estar escrito, e não descoberto.
- **A ordem operacional é migrar → construir → reiniciar.** Inverter faria a API subir contra um
  esquema que ainda tem a coluna que o código já não conhece.
- **Medição pendente, não bloqueante** (tech-alignment §5): `SELECT arquivo FROM
  identidade.migracao_aplicada ORDER BY arquivo`, com a credencial de `/etc/sysloc/migracao.env`
  (0600), **pelo operador** — não por subagente. O resultado interessa ao **D20 (F3/T7)**, cujo
  gatilho *fecha em silêncio*, e entra no `_run/run-report.md`. **Nada nesta especificação depende da
  resposta.**
- **Débitos: nenhum dispara aqui.** O **D20** não é tocado (a `0010` fica intacta); o **D14** não
  agrava (nenhum literal de fuso novo — `timestamptz` comparado com `pg_catalog.now()`); o **D12**
  não dispara (esta task não abre `packages/contracts/src/cobranca.ts`).
- **O `CT-907` é flaky pré-existente** (timeout de 5000 ms sob disputa de CPU). Falha por *timeout* é
  o flake; falha por *asserção* é achado.
