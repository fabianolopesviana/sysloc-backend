## 2. Objetivo da Task
Migrar `emitir_boleto_sicoob` para o adaptador, apontar o `SELECT ... FOR UPDATE` do sequencial para a DocType canônica e executar o corte atômico do contador (Patch 2) — no mesmo deploy, já que a emissão é a única consumidora do contador. Fecha o estrangulamento.

---

## 3. Descrição Detalhada
Três mudanças acopladas ao deploy final:

- Modificar `cobranca_sicoob/emissao.py`: manter `_validar_cobranca_e_locatario`, a instrução do boleto e o PDF privado via `salvar_pdf_privado`; substituir `pkcs12_post` + montagem inline de payload por `resolver_credenciais()` → `adaptador.emitir(boleto)`. **Guarda RN-07**: se `certificado.validade_fim < hoje` → recusa antes de qualquer HTTP (CT-024).
- Modificar `cobranca_sicoob/sequencial.py`: o `SELECT ... FOR UPDATE` aponta para `tabConfiguracao Integracao Bancaria`, preservando o formato `AAAAMM`+12 dígitos e o comportamento do lock.
- Criar `patches/v1_0/cortar_contador_sequencial.py` (Patch 2, `[post_model_sync]`): idempotente; na mesma transação copia `ultimo_sequencial_seu_numero` da legada para a canônica **e** desativa a legada — origem única. Registrar em `patches.txt` **apenas** neste commit.

Após esta task, CT-028 (erro estruturado nos 5 pontos) e CT-030 (equivalência das 5 operações) tornam-se conclusivos — escritos desde o início como esperados-a-falhar até aqui.

### 6.6 Detalhamento dos Casos de Teste

#### CT-008 — Formatação do identificador sequencial: prefixo AAAAMM + 12 dígitos zero-padded, incluindo overflow
- **Tipo/Camada**: UNITARIO · unit · CA CA-17
- **Invariante**: O identificador sequencial sempre tem o formato AAAAMM seguido de exatamente 12 dígitos zero-padded; o incremento além de 999999999999 é recusado explicitamente, nunca produz um identificador malformado ou trunca silenciosamente.
- **Pré-condições**: Nenhuma — funções puras de formatação de string/data
- **Entrada**: {"descricao": "Tabela parametrizada de valores de sequencial anterior", "valores": {"casos": [{"ultimo_sequencial": "000000000000", "data_ref": "2026-07-20", "esperado_prefixo": "202607", "esperado_novo": "000000000001"}, {"ultimo_sequencial": "999999999998", "data_ref": "2026-07-20", "esperado_novo": "999999999999"}, {"ultimo_sequencial": "999999999999", "data_ref": "2026-07-20", "esperado_erro":
- **Passos**: Para cada linha, invocar a lógica de formatação/incremento pura com ultimo_sequencial e data_ref.
- **Esperado**: "Para as 2 primeiras linhas: seu_numero == esperado_prefixo + esperado_novo, sempre 18 caracteres (6+12). Para a 3ª linha: erro explícito de limite excedido, sem gerar string."
- **Negative companion**: self — sequencial anterior == 999999999999 (próximo excede o limite de 12 dígitos) → erro de negócio explícito ('sequencial excedeu o limite'), nenhum identificador é produzido/persistido
- **Execução real**: none (fronteira HTTP mockada — provedor não é chamado)

#### CT-014 — RN-03: contador sequencial sob concorrência nunca gera nosso_numero duplicado
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: RN-03: o contador sequencial é único e contínuo; quando duas emissões concorrentes disputam o mesmo lock de linha (`SELECT ... FOR UPDATE`), cada uma recebe um sequencial estritamente distinto — nunca há duas emissões com o mesmo seu_numero/nosso_numero, independentemente de ordem de chegada.
- **Pré-condições**: Configuração ativa real no banco de teste com ultimo_sequencial_seu_numero conhecido (ex.: '000000000010'); Duas conexões de banco distintas e reais (não a mesma sessão do Frappe), cada uma em sua própria transação
- **Entrada**: {"descricao": "Duas threads/processos disparando gerar_seu_numero(data_emissao) concorrentemente para a mesma config", "valores": {"ultimo_sequencial_inicial": "000000000010", "num_chamadas_concorrentes": 2}}
- **Passos**: Preparar a configuração ativa com ultimo_sequencial_seu_numero = '000000000010' e commitar.; Disparar 2 threads (ou 2 conexões de banco separadas) que chamam a função real de geração de sequencial quase simultaneamente, cada uma dentro de sua própria transação real com commit ao final.; Aguardar as duas terminarem e coletar os dois seu_numero retornados.; Recarregar a configuração do banco após am
- **Esperado**: "Os dois seu_numero retornados são diferentes entre si (um é '...000011', outro '...000012', em qualquer ordem); o ultimo_sequencial_seu_numero final no banco é exatamente '000000000012' (nunca '000000000011' repetido, nunca um valor perdido)."
- **Negative companion**: self — duas conexões de banco reais e concorrentes chamando `gerar_seu_numero` para a mesma configuração ativa, sem serialização externa → os dois sequenciais retornados são diferentes e o valor final persistido é exatamente inicial+2 (nenhuma leitura perdida, nenhuma sobrescrita)
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-015 — RN-03: contador sequencial nunca reinicia ao trocar de conta bancária
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: RN-03: trocar a conta bancária ativa não reinicia o contador sequencial — o próximo valor gerado após a troca é estritamente maior que o último valor gerado antes da troca, mesmo que a troca envolva desativar uma configuração e ativar outra.
- **Pré-condições**: Duas configurações no banco de teste (A ativa com sequencial em '000000000100', B inativa)
- **Entrada**: {"descricao": "Sequência: gerar em A, desativar A e ativar B (preservando a origem única do contador), gerar novamente", "valores": {"sequencial_inicial_A": "000000000100"}}
- **Passos**: Gerar um seu_numero com a configuração A ativa; anotar o valor numérico.; Executar a troca de configuração ativa (desativar A, ativar B), preservando a origem única do contador conforme D3.; Gerar um novo seu_numero com B agora ativa.
- **Esperado**: "O valor numérico do segundo seu_numero é estritamente maior que o do primeiro (nunca reinicia para '000000000001' ou qualquer valor menor que o anterior)."
- **Negative companion**: self — gerar sequencial na config A, trocar para config B, gerar novamente — assert de que NÃO reiniciou seria a falha → o sequencial pós-troca é estritamente maior que o pré-troca; nunca reinicia para valores baixos
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-024 — CA-15/RN-07: emissão com certificado vencido é recusada com mensagem de negócio ANTES de qualquer chamada HTTP ao banco
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-15
- **Invariante**: RN-07: com o certificado em uso vencido, a emissão de boleto é recusada com mensagem de negócio explicando vencimento e ação necessária, e o cliente HTTP do adaptador NUNCA é invocado — a checagem de validade ocorre estritamente antes da tentativa de rede.
- **Pré-condições**: Configuração ativa com certificado cuja data de validade já expirou (fixture com validade no passado); Cobranca válida e elegível para emissão no banco de teste
- **Entrada**: {"descricao": "Cobranca elegível + configuração com certificado vencido", "valores": {"data_validade_certificado": "2026-01-01"}}
- **Passos**: Instrumentar (patch com contador de chamadas) o ponto de chamada HTTP do adaptador (`requests_pkcs12.post`) usado para obter token/emitir.; Chamar o serviço de emissão de boleto para a cobrança elegível.; Verificar o contador de chamadas do mock HTTP e a mensagem retornada.
- **Esperado**: "Retorno {success: False, message: <negócio, menciona vencimento e ação necessária>}; contador de chamadas do mock HTTP == 0 (nem obter_token nem emitir foram tentados)."
- **Negative companion**: self — n/a — este é o próprio caso negativo de uma emissão normal com certificado válido → mock do cliente HTTP tem contador de chamadas == 0 após a tentativa de emissão
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-027 — D3: contador sequencial migra em corte único e atômico, sem fallback de leitura para a origem legada
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: D3 (exceção explícita ao fallback geral): após o corte de migração do contador sequencial, a geração de sequencial usa exclusivamente a nova origem — nenhuma leitura, nem mesmo em caminho de erro, recai sobre o campo legado `ultimo_sequencial_seu_numero` da configuração antiga.
- **Pré-condições**: Migração de contador já executada (corte realizado); campo legado do contador ainda fisicamente presente na configuração antiga por herança de schema, mas não mais lido
- **Entrada**: {"descricao": "Sequencial legado alterado para um valor visivelmente diferente após o corte", "valores": {"sequencial_legado_pos_corte": "000000000001", "sequencial_canonico_real": "000000000500"}}
- **Passos**: Após simular o corte de migração, alterar diretamente (via `frappe.db.set_value`) o campo legado do contador para um valor baixo e distinto do canônico.; Chamar a função real de geração de sequencial.
- **Esperado**: "O sequencial gerado continua a partir do valor CANÔNICO (ex.: '000000000501'), nunca do valor legado alterado ('000000000002') — prova de que não existe leitura de fallback para o contador pós-corte."
- **Negative companion**: self — campo legado do contador é alterado manualmente após o corte (simulando uma leitura indevida da origem antiga) → o próximo sequencial gerado ignora completamente o valor alterado no campo legado — prova de que não há fallback de leitura para o contador
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-028 — Resolução de configuração unificada produz erro estruturado idêntico nos 5 pontos de consumo (auth, emissão, consulta, baixa, confirmação)
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: A fonte única de resolução de configuração (que substitui as 5 cópias hoje duplicadas — 1 estruturada, 4 em texto cru) produz o MESMO shape de erro para os 5 pontos de consumo do adaptador quando não há configuração ativa válida.
- **Pré-condições**: Nenhuma configuração ativa no banco de teste (site limpo desse aspecto)
- **Entrada**: {"descricao": "As 5 operações do adaptador chamadas em sequência sobre o mesmo estado (config ausente)", "valores": {"operacoes": ["obter_token", "emitir", "consultar", "solicitar_baixa", "confirmar_baixa"]}}
- **Passos**: Para cada uma das 5 operações do ponto de entrada (via o serviço/adaptador correspondente), invocar a operação sem nenhuma configuração ativa presente.; Coletar o erro retornado por cada uma.
- **Esperado**: "Os 5 erros retornados têm exatamente o mesmo conjunto de chaves top-level (ex.: {success, message, ...}) — nenhum devolve string crua onde os outros devolvem dict estruturado."
- **Negative companion**: self — zero configurações ativas, testado a partir de cada um dos 5 pontos de consumo → todos os 5 pontos retornam erro estruturado com o MESMO conjunto de chaves (não mais 1 dict vs. 4 strings)
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-030 — CA-17: as chaves de resposta das 5 operações de cobrança permanecem equivalentes ao contrato observável anterior
- **Tipo/Camada**: E2E · e2e · CA CA-17
- **Invariante**: CA-17: para as operações emitir, baixar, consultar, confirmar e sincronizar, o conjunto de chaves top-level do dict de resposta que o cliente já consome hoje permanece presente e com os mesmos nomes — o refactor interno (ADR-0001) não altera o contrato observável, só a implementação por trás dele.
- **Pré-condições**: Cobrança elegível para emissão real no banco de teste; chamada HTTP ao provedor mockada com uma resposta de sucesso representativa para cada uma das 5 operações
- **Entrada**: {"descricao": "Conjunto de chaves contrato imutável declarado nas instruções do orquestrador", "valores": {"chaves_contrato": ["success", "cobranca_id", "nosso_numero", "codigo_barras", "linha_digitavel", "qr_code_pix", "pdf_boleto_arquivo", "pdf_boleto_url", "boleto_gerado", "situacao_boleto_sicoob", "pagamento_confirmado", "status_cobranca", "valor_pago", "data_pagamento"]}}
- **Passos**: Para cada uma das 5 operações (emitir, baixar, consultar, confirmar, sincronizar), mockar a resposta HTTP do provedor com um payload de sucesso mínimo e chamar o método whitelisted correspondente sobre uma cobrança real do banco de teste.; Coletar o dict de retorno de cada chamada.; Para cada chave da lista `chaves_contrato` que é semanticamente aplicável àquela operação, verificar presença no dic
- **Esperado**: "Nenhuma chave do contrato imutável aplicável a cada operação está ausente no dict retornado pós-refactor; os tipos (str/bool/float/None) de cada chave batem com o comportamento documentado hoje."
- **Negative companion**: self — n/a — a assertion de conjunto de chaves É o teste negativo embutido: qualquer chave ausente ou renomeada falha o teste → toda chave do contrato imutável está presente com o nome exato; nenhuma chave adicional obrigatória foi removida
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)
