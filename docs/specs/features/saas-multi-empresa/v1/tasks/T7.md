## 2. Objetivo da Task
Migrar os dois endpoints que pertencem a módulos já existentes e desativar os 6 Server Scripts, fechando o critério de nenhuma regra ativa fora do repositório.

---

## 3. Descrição Detalhada
Dois endpoints vão para módulos que já existem e já são donos do domínio:

- **`auth_locacao_imoveis`** → `usuario_app/service.py`, que já concentra a autenticação do aplicativo (`verificar_senha_usuario_app`).
- **`automacao_cobranca_config_api`** → `cobranca_automation/service.py`, dono da automação de cobrança.

Mesma ordem obrigatória das anteriores: registrar função e alias juntos, comprovar equivalência, desativar depois.

**Encerramento**: com os 6 endpoints e regras migrados e verificados, desativar os 6 Server Scripts originais. Este é o passo que fecha o CA-03 e a RN-01 — nenhuma regra de negócio ativa vive apenas no ambiente de execução.

O descarte dos 19 já desativados é da T3; esta task trata dos 6 que estavam ativos.

### 6.6 Detalhamento dos Casos de Teste

#### CT-019 — Os 4 nomes curtos resolvem para função existente via override_whitelisted_methods

- **Tipo**: UNITARIO | **Categoria**: caminho_feliz | **Camada**: Composição (hooks.py override_whitelisted_methods)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_endpoints_migrados.py`
- **Invariante**: Cada um dos 4 nomes curtos (`all_imoveis`, `auth_locacao_imoveis`, `atualizar_comodo`, `automacao_cobranca_config_api`) registrado em `override_whitelisted_methods` resolve, pelo mecanismo real do framework (`frappe.get_hooks` + `frappe.get_attr`), para uma função existente e chamável — RN-04/ADR-0004.
- **Fronteira real de execução**: none
- **Pré-condições**: `hooks.py` registra os 4 aliases
- **Passos**:
  1. Ler `frappe.get_hooks('override_whitelisted_methods')`
  2. Para cada um dos 4 nomes curtos, resolver o dotted path via `frappe.get_attr`
  3. Confirmar que o resultado é `callable`
- **Resultado esperado**: Os 4 nomes curtos estão presentes no dict; `frappe.get_attr` resolve os 4 sem exceção; `callable(resolvido) is True` para os 4
- **Companheiro negativo**: `CT-020` — entrada: alias apontando para dotted path renomeado/inexistente → `frappe.get_attr` levanta `AttributeError`/`ModuleNotFoundError` — falha determinística, não silenciosa
- **Observações**: Mesmo mecanismo de resolução de CT-064 em test_patch_criar_papel_servico_app.py (frappe.get_hooks + frappe.get_attr), aplicado a override_whitelisted_methods em vez de after_migrate.

#### CT-020 — Alias apontando para função renomeada/inexistente é detectado, não falha silenciosamente

- **Tipo**: UNITARIO | **Categoria**: tratamento_erro | **Camada**: Composição (hooks.py override_whitelisted_methods)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_endpoints_migrados.py`
- **Invariante**: Se o alias de um dos 4 nomes curtos apontar para uma função que não existe mais (renomeada sem atualizar `hooks.py`), a resolução falha explicitamente, expondo o defeito antes que o aplicativo receba 404 silencioso.
- **Fronteira real de execução**: none
- **Pré-condições**: Dotted path fabricado no próprio teste apontando para símbolo inexistente (ex.: `locacao_automation.imovel.service.funcao_que_nao_existe`)
- **Passos**:
  1. Chamar `frappe.get_attr('locacao_automation.imovel.service.funcao_que_nao_existe')`
  2. Capturar a exceção
- **Resultado esperado**: `AttributeError` (ou `ModuleNotFoundError`) é lançada — o teste falha de forma audível se o mecanismo silenciar o erro em vez de propagá-lo
- **Companheiro negativo**: `self` — entrada: este é o companion negativo de CT-019 → ver resultado_esperado
- **Observações**: Risco herdado da ADR-0004, registrado no tech_spec §20 ('alias resolver para função inexistente após renomeação futura, quebrando o aplicativo sem erro de build').

#### CT-022 — auth_locacao_imoveis autentica credencial válida e retorna sessão

- **Tipo**: INTEGRACAO | **Categoria**: caminho_feliz | **Camada**: Endpoint HTTP whitelisted (usuario_app/service.py)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_usuario_app_api.py`
- **Invariante**: Com credencial válida, `auth_locacao_imoveis` retorna 200 e uma sessão do app — comportamento idêntico ao Server Script original.
- **Fronteira real de execução**: db
- **Pré-condições**: `Usuario` (custom, app-consumido) existente com credencial de teste válida
- **Passos**:
  1. Autenticar como usuário de serviço
  2. Chamar `auth_locacao_imoveis` com credenciais válidas
  3. Verificar status e corpo da resposta
- **Resultado esperado**: Status 200; resposta contém identificador de sessão do app (mesmo campo que o SPA já consome)
- **Companheiro negativo**: `CT-023` — entrada: credencial inválida (senha incorreta) → 401, sem revelar se o email existe
- **Pré-condição privilegiada**: Endpoint exige token do usuário de serviço para o app chamar em nome do locatário/proprietário. — caminho legítimo: Mesmo caminho de CT-021 (`add_roles('Servico App')` + `frappe.set_user` + `addCleanup`).
- **Observações**: Novo arquivo (`test_usuario_app_api.py`) — nenhuma suíte hoje cobre o comportamento deste endpoint especificamente.

#### CT-023 — Credencial inválida em auth_locacao_imoveis retorna 401 sem revelar existência do email

- **Tipo**: SEGURANCA | **Categoria**: seguranca | **Camada**: Endpoint HTTP whitelisted (usuario_app/service.py)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_usuario_app_api.py`
- **Invariante**: Uma credencial inválida (email inexistente OU senha errada) retorna 401 com a mesma mensagem/forma em ambos os casos — a resposta não permite distinguir se o email existe.
- **Fronteira real de execução**: db
- **Pré-condições**: `Usuario` de teste existente com senha conhecida
- **Passos**:
  1. Chamar `auth_locacao_imoveis` com (a)
  2. Registrar status e corpo
  3. Chamar `auth_locacao_imoveis` com (b)
  4. Comparar status e corpo com (a)
- **Resultado esperado**: Ambas as chamadas retornam 401 com mensagem/formato idênticos entre si — nenhuma pista (tempo de resposta, texto, campo extra) diferencia email existente de inexistente
- **Companheiro negativo**: `self` — entrada: este é o companion negativo de CT-022 → ver resultado_esperado
- **Pré-condição privilegiada**: Mesma precondição de CT-022. — caminho legítimo: Mesmo caminho de CT-022.
- **Observações**: Preserva o mapeamento de erro documentado em tech_spec §10.1 (401 do framework, sem revelar existência).

#### CT-026 — automacao_cobranca_config_api preserva leitura e escrita da configuração vigente

- **Tipo**: INTEGRACAO | **Categoria**: integracao | **Camada**: Endpoint HTTP whitelisted (cobranca_automation/service.py)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_cobranca_automation_config_api.py`
- **Invariante**: GET retorna a configuração de automação de cobrança vigente; POST persiste uma nova configuração — o formato de payload/resposta é idêntico ao do Server Script original.
- **Fronteira real de execução**: db
- **Pré-condições**: `Automacao Cobranca Config` vigente existente
- **Passos**:
  1. Autenticar como usuário de serviço
  2. Chamar GET e capturar a configuração vigente
  3. Chamar POST com nova configuração
  4. Chamar GET novamente
- **Resultado esperado**: 1º GET retorna a configuração vigente antes da mudança; POST retorna 200 confirmando persistência; 2º GET retorna exatamente os valores enviados no POST
- **Companheiro negativo**: `self` — entrada: POST com payload de configuração inválido (ex.: horário fora de faixa) → erro de validação, mapeado ao status já documentado; configuração vigente anterior permanece inalterada
- **Pré-condição privilegiada**: Endpoint exige token do usuário de serviço. — caminho legítimo: Mesmo caminho de CT-021.
- **Observações**: Contribui à rede de regressão de CA-11 (rotina automática de cobrança) junto às caracterizações CT-014/CT-015.

#### CT-027 — Ao final, nenhum Server Script das 6 regras migradas permanece ativo

- **Tipo**: INTEGRACAO | **Categoria**: integridade_dados | **Camada**: Integridade de regra de negócio (Server Script)
- **Arquivo**: `app-sync/locacao_automation/locacao_automation/tests/test_server_scripts_desativados.py`
- **Invariante**: Nenhuma regra de negócio ativa existe apenas no ambiente de execução (RN-01) — ao fim da migração, os 6 Server Scripts correspondentes (2 de DocType Event + 4 de API) estão desabilitados ou ausentes.
- **Fronteira real de execução**: db
- **Pré-condições**: Lista fechada dos 6 nomes de Server Script originais (2 DocType Event + 4 API), documentada no tech_spec/pre-refinement
- **Passos**:
  1. Consultar `frappe.db.count('Server Script', {'name': ['in', <6 nomes>], 'disabled': 0})`
- **Resultado esperado**: Contagem igual a 0 — nenhum dos 6 Server Scripts originais está habilitado (RN-08: a original só é desativada após equivalência comprovada, mas ao final deste teste NENHUMA das duas formas — original e migrada — pode estar simultaneamente ativa)
- **Companheiro negativo**: `self` — entrada: qualquer um dos 6 Server Scripts encontrado com `disabled=0` É o modo de falha desta invariante → contagem de Server Scripts ativos entre os 6 nomes conhecidos é 0
- **Observações**: Só é executado depois que CT-014/CT-015 (equivalência) estiverem verdes — verificação de estado FINAL, não de transição. Novo arquivo justificado: nenhuma suíte hoje consulta o DocType `Server Script`.
