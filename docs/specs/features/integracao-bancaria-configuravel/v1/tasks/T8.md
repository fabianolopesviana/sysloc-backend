## 2. Objetivo da Task
Migrar `solicitar_baixa_boleto_sicoob` e `confirmar_baixa_boleto_sicoob` para o adaptador, preservando assinaturas, chaves de resposta e chaves de idempotência.

---

## 3. Descrição Detalhada
Modificar `cobranca_sicoob/baixa.py` e `confirmacao_baixa.py`: substituir `pkcs12_post`/`pkcs12_get`, `SICOOB_BOLETOS_URL` e as cópias de `_obter_configuracao_ativa` por `resolver_credenciais()` → `adaptador.solicitar_baixa(ref)` / `adaptador.confirmar_baixa(ref)`. Preservar as chaves (`success`, `cobranca_id`, `nosso_numero`, `baixa_solicitada`/`baixa_confirmada`, `situacao_boleto_sicoob`) e as chaves de idempotência dos eventos. Dependência sequencial de T7 encoda a ordem do estrangulamento (baixa depois de consulta validada em produção).

### 6.6 Detalhamento dos Casos de Teste

#### CT-113 — solicitar_baixa_boleto_sicoob — equivalência do caminho feliz
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: Dado 204 No Content do provedor, a resposta de solicitar_baixa_boleto_sicoob e o evento registrado são idênticos ao comportamento pré-refactor.
- **Pré-condições**: Cobranca com nosso_numero, numero_cliente_sicoob, codigo_modalidade_sicoob preenchidos; Configuração ativa válida
- **Entrada**: {"descricao": "Mock token 200 + mock POST de baixa retornando 204", "valores": {"baixa_response": {"status_code": 204, "text": ""}}}
- **Passos**: Preparar fixtures; Patchar cliente HTTP centralizado; Chamar solicitar_baixa_boleto_sicoob(cobranca.name); Consultar o evento Cobranca Integracao Sicoob criado
- **Esperado**: "retorno == {'success': True, 'cobranca_id': cobranca_id, 'nosso_numero': nosso_numero, 'baixa_solicitada': True} (chave-a-chave); evento com tipo_evento='boleto_baixa_solicitada', status_processamento='processado', idempotencia_chave == f'boleto_baixa_solicitada:{cobranca_id}:{nosso_numero}'."
- **Negative companion**: CT-114 — resposta HTTP >= 400 na solicitação de baixa → success:False, baixa_solicitada:False, status_code presente, evento com status_processamento='erro'
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-114 — solicitar_baixa_boleto_sicoob — falha HTTP preserva shape de erro

- **Invariante**: Resposta de erro do provedor na solicitação de baixa produz o mesmo shape de erro (incluindo status_code) do comportamento pré-refactor.

- **Esperado**: "retorno['success'] is False; retorno['baixa_solicitada'] is False; retorno['status_code'] == 422; evento com status_processamento='erro' e mesma idempotencia_chave de CT-113; mensagem de erro contém o texto do corpo retornado ('Boleto ja baixado')."

#### CT-119 — Chave de idempotência de baixa/confirmação é determinística entre chamadas
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-17
- **Invariante**: A idempotencia_chave dos eventos de solicitação e confirmação de baixa é função pura de (cobranca_id, nosso_numero) — não incorpora timestamp, uuid ou contador de tentativa.
- **Pré-condições**: Cobranca válida com nosso_numero preenchido
- **Entrada**: {"descricao": "Duas chamadas sucessivas de solicitar_baixa_boleto_sicoob e duas de confirmar_baixa_boleto_sicoob, mesma Cobranca/nosso_numero", "valores": {}}
- **Passos**: Mockar respostas de sucesso para ambas as chamadas; Chamar solicitar_baixa_boleto_sicoob(cobranca.name) duas vezes; Chamar confirmar_baixa_boleto_sicoob(cobranca.name) duas vezes; Consultar os 4 eventos Cobranca Integracao Sicoob criados
- **Esperado**: "Os dois eventos de solicitação têm idempotencia_chave idêntica igual a 'boleto_baixa_solicitada:{cobranca_id}:{nosso_numero}'; os dois eventos de confirmação têm idempotencia_chave idêntica igual a 'boleto_baixa_confirmada:{cobranca_id}:{nosso_numero}'."
- **Negative companion**: self — implementação alternativa hipotética que gerasse a chave via uuid/timestamp (não determinística) → duas chamadas com os mesmos parâmetros produzem SEMPRE a mesma idempotencia_chave; a chave só muda se cobranca_id ou nosso_numero mudar
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)
