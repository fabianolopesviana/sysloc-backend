Patch idempotente que copia a configuração legada para a canônica — SEM copiar o contador e SEM desativar a legada, para não quebrar as operações ainda não portadas.

## 3. Descrição Detalhada
Criar `patches/v1_0/migrar_configuracao_integracao_bancaria.py` e registrá-lo em `patches.txt` sob `[post_model_sync]`:

- Se já existe canônica ativa para `Sicoob` → encerra sem escrita (idempotência).
- Copia da legada ativa: `client_id`, `token_url`→`auth_url`, `scope`, `numero_cliente_sicoob`→`numero_cliente`, `codigo_modalidade_sicoob`→`codigo_modalidade`, `numero_conta_corrente_sicoob`→`numero_conta_corrente`, `pfx_path`→`pfx_path_legado`, senha via `get_password`. `api_base_url` recebe o valor da constante removida.
- **NÃO copia `ultimo_sequencial_seu_numero` e NÃO desativa a legada** — isso é do Patch 2 (T10), acoplado ao deploy da emissão. Desativar aqui zeraria a config ativa das 4 operações não portadas → quebra CA-16.
- Registra a migração na auditoria.

Criar também os marcadores `patches/__init__.py` e `patches/v1_0/__init__.py`.

### 6.6 Detalhamento dos Casos de Teste

#### CT-026 — D3: patch de migração da configuração legada para a canônica é idempotente
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-16
- **Invariante**: D3: executar o patch de migração da configuração mais de uma vez não duplica registros nem corrompe a configuração canônica já copiada — o resultado após 2 execuções é idêntico ao resultado após 1 execução.
- **Pré-condições**: Configuração legada real no banco de teste (DocType `Configuracao Integracao Sicoob`) com dados completos
- **Entrada**: {"descricao": "Execução do patch de migração duas vezes seguidas", "valores": {}}
- **Passos**: Executar o patch de migração da configuração uma primeira vez.; Capturar snapshot da configuração canônica resultante (contagem de registros + campos).; Executar o mesmo patch uma segunda vez.; Capturar novo snapshot e comparar.
- **Esperado**: "Contagem de registros da configuração canônica é idêntica antes e depois da 2ª execução; nenhum campo divergente entre os dois snapshots."
- **Negative companion**: self — executar o patch uma segunda vez sobre um estado já migrado → nenhum registro duplicado é criado; campos permanecem idênticos ao estado pós-primeira-execução
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)
