## 2. Objetivo da Task

Estabelecer a raiz do monorepo: versão do runtime e das ferramentas fixadas por arquivo versionado, workspace declarado, orquestrador de build configurado, formatador/linter único e TypeScript estrito compartilhado. Ao final, o repositório é instalável e construível — ainda sem nenhum pacote com conteúdo.

Esta task não cria aplicação alguma. Ela cria o **chão** sobre o qual T3, T5 e T6 constroem.

#### CT-002 — A configuração da raiz não é declarativa: TypeScript estrito, formatador e contrato de ambiente (parametrizado, 4 cenários)

- **Invariant**: `tsconfig.base.json`, `biome.json` e `turbo.json` não são declarativos: um membro do workspace que viola os dois primeiros faz `pnpm build` e `pnpm lint` saírem com código != 0, nomeando a violação; e o ambiente declarado no terceiro chega de fato à tarefa, enquanto o não declarado não chega.
- **Owning layer**: `service-integration` | **Real execution boundary**: `filesystem`

  - CT-001 aprovado no mesmo clone efêmero (ferramental instalado e ciclo limpo comprovado)

- **Dados de entrada**: Dois cenários de violação (A e B), cada um com sua porta de qualidade correspondente; um cenário de controle (C); e um cenário de contrato de ambiente (D) com as cinco variáveis do `.env.example` exportadas mais uma variável de controle deliberadamente não declarada no `turbo.json`

  1. Criar o pacote temporário no clone efêmero com o `tsconfig.json` estendendo o base, sem sobrescrever opções
  2. Cenário A: escrever o arquivo com o parâmetro implicitamente `any`, executar `pnpm build`, registrar código de saída e a saída completa
  3. Cenário B: escrever o arquivo fora de formato, executar `pnpm lint`, registrar código de saída e a saída completa
  4. Cenário C (controle): corrigir as duas violações e reexecutar `pnpm build` e `pnpm lint`
  5. Cenário D: exportar `NODE_ENV`, `DATABASE_URL`, `REDIS_URL`, `PORT`, `LOG_LEVEL` e uma variável de controle não declarada no `turbo.json`, executar `pnpm test` (a tarefa `test` já declarada — nenhuma tarefa é criada só para o teste enxergar) e registrar o que o processo da tarefa observou em cada uma

Cenário B: `pnpm lint` sai != 0 e a saída nomeia o caminho do arquivo violador. Cenário C (controle): com as violações corrigidas, `pnpm build` e `pnpm lint` voltam a sair 0. A transição !=0 → 0 é o que distingue uma porta de qualidade real de um comando que falharia por qualquer motivo. Cenário D: `pnpm test` sai 0; as cinco variáveis declaradas no `turbo.json` (`NODE_ENV` por `globalEnv`; `DATABASE_URL`, `REDIS_URL`, `PORT` e `LOG_LEVEL` por `env` da tarefa `test`) chegam ao processo da tarefa com o **valor exato** exportado; e a variável de controle, não declarada, chega **ausente** — o Turborepo 2.x roda em Strict Environment Mode e remove o que não está declarado. O par declarada/não-declarada é o que impede a asserção tautológica: sem o segundo lado, "chegou" não distinguiria declaração efetiva de repasse acidental.

Proibido, para fazer o caso rodar: relaxar regra do `biome.json`/`tsconfig.base.json`, adicionar arquivo de exceção/ignore, ou marcar o pacote como excluído do workspace — qualquer uma dessas concessões desliga em produção justamente a porta que o caso existe para provar. Análogo: `NENHUM`

O cenário C impede a asserção tautológica (AP-29): sem ele, um `pnpm build` quebrado por qualquer outra razão passaria como sucesso do caso.

  3. Contar as linhas de variável de segredo com valor concreto
  4. Varrer o arquivo por host, IP ou porta do ambiente legado
  5. Conferir que o arquivo tem ao menos uma linha de comentário descrevendo o propósito de cada bloco de variáveis

A asserção é sobre a árvore versionada (`git ls-files`), não sobre o disco, seguindo o precedente de `verificar-golden.sh:78`.

#### CT-004 — Arquivo de ambiente com valor real é barrado pelo Git e recusado por `git add`

- **Tipo**: Segurança | **Categoria**: teste_negativo
- **Arquivo**: `deploy/scripts/instalacao/verificar-workspace.sh` (criado)
- **Invariant**: Um `.env` contendo credencial, criado na raiz de um repositório governado pelo `.gitignore` versionado, é ignorado pelo Git e recusado por `git add` sem `--force` — o descuido não vira commit.
- **Owning layer**: `service-integration` | **Real execution boundary**: `filesystem`
- **Pré-condições**:
  - **O caso roda dentro do clone efêmero do CT-001, nunca na árvore de trabalho do operador.** O SUT é o `.gitignore` versionado, presente byte a byte no clone; `git check-ignore`, `git add` e `git status` se comportam de forma idêntica ali. Como consequência, o caso não depende do estado da árvore de trabalho: um `.env` na raiz do repositório — o estado que o próprio `.env.example` recomenda — é irrelevante para a bateria, e nenhum arquivo do operador é lido, movido ou reescrito
  - Não há resguardo de arquivo pré-existente, porque não há o que resguardar. A precondição inversa é asserida: o clone **não pode** ter herdado `.env`, `.env.local` nem `.env.producao` — se herdou, a construção do sandbox está furada e o caso estaria medindo o arquivo errado
  - Estado de `git status --porcelain` do clone capturado antes do caso, para comparação ao final
  - Traps de limpeza (EXIT, INT, TERM, HUP) armados antes de criar qualquer arquivo — eles removem o clone inteiro, o que é a limpeza completa do caso
- **Dados de entrada**: Três nomes de arquivo de ambiente, cada um com uma linha de credencial fictícia gerada em runtime
- **Passos**:
  1. Conferir que o clone efêmero não herdou nenhum dos três arquivos, e capturar o `git status --porcelain` do clone
  2. Criar os três arquivos no clone, com a credencial fictícia gerada em runtime
  3. Para cada um: executar `git check-ignore -q` e registrar o código de saída
  4. Executar `git status --porcelain` e contar as ocorrências dos três nomes
  5. Executar `git add .env` (sem `--force`) e registrar código de saída e mensagem
  6. Conferir que `.env.example` continua rastreável — `git check-ignore -q .env.example` sai != 0
  7. Remover os três arquivos e conferir que `git status --porcelain` voltou ao estado inicial
- **Resultado esperado**: `git check-ignore -q` sai 0 para `.env`, `.env.local` e `.env.producao`. `git status --porcelain` lista 0 ocorrências dos três nomes. `git add .env` sai != 0 com a mensagem contendo `ignored by one of your .gitignore files`. `git check-ignore -q .env.example` sai != 0 — a negação `!.env.example` continua valendo, senão a documentação de configuração sumiria junto. Após a limpeza, `git status --porcelain` é byte a byte idêntico ao capturado no início do caso.
- **Negative companion**: este é o caso negativo (`ct_id: self`) — entrada: este é o caso negativo — `.env`, `.env.local` e `.env.producao` com credencial fictícia. Asserção: ver resultado_esperado
- **Precondição privilegiada**: Criar os três arquivos **dentro do clone efêmero**, nunca na árvore de trabalho do operador — o sandbox já existe e carrega o mesmo SUT, então mutar a árvore real seria risco sem contrapartida (o resguardo compensatório não cobre SIGKILL, corte de energia nem execução concorrente). Gerar o valor fictício em runtime (bytes de `/dev/urandom` codificados), nunca reutilizar credencial real de nenhum ambiente, nunca versionar o valor nem seu hash, e remover os arquivos no encerramento do caso — inclusive em falha ou por sinal, via trap. Conferir ao final que `git status --porcelain` voltou exatamente ao estado capturado no início do caso. Proibido relaxar o `.gitignore` para fazer o caso rodar. Análogo: `deploy/scripts/caracterizacao/preparar-site-efemero.sh — geração de senha efêmera em runtime (linhas 150-151) e leitura de credencial sem eco (linhas 57-75)`
- **Critérios validados**: CA-12; CLAUDE.md — invariante 3 (nenhum segredo versionado)
- **Obs**: O CT-003 continua legitimamente sobre `RAIZ_REPO` — lá o objeto é a árvore versionada real (`git ls-files .env.example`), que o clone não substitui. Complementa CT-003 pelo lado do modo de falha: CT-003 prova que o arquivo documentado está limpo, este prova que o arquivo real não consegue entrar. A asserção sobre `.env.example` continuar rastreável não é decorativa — um `.gitignore` endurecido sem a linha de negação passaria em todas as demais asserções deste caso e quebraria CT-003 silenciosamente.
