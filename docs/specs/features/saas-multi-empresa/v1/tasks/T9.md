## 2. Objetivo da Task
Montar o ambiente novo isolado, com banco vazio, recebendo a estrutura inteira do repositório — o que torna a reconstrução do zero verificável de fato.

---

## 3. Descrição Detalhada
A stack nova sobe como projeto de composição próprio, com nome de projeto, portas e volumes distintos dos atuais, reusando as mesmas imagens já em uso. Nenhuma imagem nova é introduzida.

**Banco vazio é requisito, não conveniência**: a estrutura vem inteira do repositório. Provar reconstrução do zero contra um ambiente que já tem dados não prova nada — é a razão de o `CT-028` só ser honesto aqui.

**Isolamento obrigatório**: as portas não são expostas ao proxy do aplicativo, e o proxy da contenção anterior continua apontando exclusivamente para o ambiente atual. A stack nova **não deve** ser alcançável pelo aplicativo publicado (RN-06).

Ao responder, este ambiente passa a ser o destino da suíte (ADR-0006), encerrando o maior raio de dano do repositório.

#### CT-028 — Ambiente novo com banco vazio reconstrói a fundação completa a partir do repositório

- **Invariante**: Aplicar a estrutura do repositório a um ambiente com banco vazio produz todos os cadastros do domínio, sem nenhuma intervenção manual (CA-01).
- **Fronteira real de execução**: db
- **Pré-condições**: Stack nova (`deploy/compose/docker-compose.stack-nova.yaml`) disponível; Site novo criado com banco vazio
- **Passos**:
  1. Criar site vazio
  2. Instalar o app
  3. Rodar `bench migrate`
  4. Listar DocTypes do módulo `Locacao Automation`
- **Resultado esperado**: Os 14 DocTypes preservados + os 2 já versionados existem com `custom=0`; nenhum erro de migração; nenhum passo manual adicional foi necessário
- **Companheiro negativo**: `CT-029` — entrada: reaplicar a mesma migração sobre o ambiente já estruturado → nenhum cadastro duplicado, nenhum dado alterado
- **Pré-condição privilegiada**: Verificação de reconstrução completa exige um banco de dados vazio de verdade (sem os 19 cadastros preexistentes) — irreproduzível dentro de uma transação de `FrappeTestCase` contra um site já populado (`frontend` ou qualquer clone com dados). — caminho legítimo: Subir a stack nova (`docker compose -f deploy/compose/docker-compose.stack-nova.yaml up -d`); criar site vazio (`bench new-site <site-novo>`); instalar o app (`bench --site <site-novo> install-app locacao_automation`); rodar `bench --site <site-novo> migrate`; inspecionar via `bench --site <site-novo> console` ou suíte apontada para `<site-novo>` — nunca `frontend`. É exatamente o destino que ADR-0006/D5 prevê para a suíte assim que o ambiente novo responder.
- **Observações**: Bloqueado operacionalmente enquanto o ambiente novo não responder (trade-off aceito em D5) — a rodada real só é possível após a subida da stack nova.

### 7.A.2 — Subida da stack (e um defeito real encontrado na primeira tentativa)

A primeira subida **falhou**, e o defeito é informação:

```
 Container frappe-stack-nova-configurator-1 Error service "configurator" didn't complete successfully: exit 1
service "configurator" didn't complete successfully: exit 1

$ docker compose -f deploy/compose/docker-compose.stack-nova.yaml logs configurator | tail -5
configurator-1  |   File "/home/frappe/frappe-bench/apps/frappe/frappe/__init__.py", line 1441, in get_module
configurator-1  |     return importlib.import_module(modulename)
configurator-1  | ModuleNotFoundError: No module named 'locacao_automation'
```

**Causa**: a primeira linha do `command` do configurator é `ls -1 apps > sites/apps.txt`. Como o bind mount do app existe desde a subida, o `apps.txt` nasce contendo `locacao_automation` — e todo `bench set-config` seguinte chama `setup_module_map()` sobre **todo** app do `apps.txt`. Sem `PYTHONPATH`, o configurator morre importando o app que ele acabou de registrar. Corrigido acrescentando `PYTHONPATH` ao serviço `configurator` (o `backend` já o tinha, por espelhar o override de produção).

> **Achado colateral, registrado e não tocado**: no ambiente atual o `sites/apps.txt` contém apenas `erpnext` e `frappe` — o `locacao_automation` **não** está lá, embora esteja instalado no site `frontend` (`bench --site frontend list-apps` lista os três). O configurator de produção rodou antes de o bind mount existir e nunca reprocessou. Na stack nova o `apps.txt` nasce correto (7.A.3). Não é escopo desta task mexer nisso.

Segunda subida, bem-sucedida:

### 7.A.7 — O experimento decisivo: o que `remove_orphan_doctypes` faz de verdade

A T1 foi bloqueada porque nunca exerceu `remove_orphan_doctypes()`. Com o ambiente destrutível de pé, o mecanismo pôde ser exercido contra um alvo descartável. Fonte, lida no contêiner (`apps/frappe/frappe/model/sync.py:142`):

```python
def remove_orphan_doctypes():
	"""Find and remove any orphaned doctypes.
	...
	Note: Deleting the entry doesn't delete any data.
	So this is supposed to be non-destrictive operation.
	"""
	doctype_names = frappe.get_all("DocType", {"custom": 0}, pluck="name")
	orphan_doctypes = []
	clear_controller_cache()
	class_overrides = frappe.get_hooks("override_doctype_class", {})
	for doctype in doctype_names:
		if doctype in class_overrides:
			continue
		try:
			get_controller(doctype=doctype)
		except ImportError:
			orphan_doctypes.append(doctype)
		except Exception:
			continue
	if not orphan_doctypes:
		return
	print(f"Orphaned DocType(s) found: {', '.join(orphan_doctypes)}")
	for i, name in enumerate(orphan_doctypes):
		frappe.delete_doc("DocType", name, force=True, ignore_missing=True)
		update_progress_bar("Deleting orphaned DocTypes", i, len(orphan_doctypes))
	frappe.db.commit()
```

O filtro é `{"custom": 0}` — **sem** filtro de módulo ou de app. O critério de órfão é: `get_controller()` levantar `ImportError`.

**Reprodução exata do cenário que a T2 vai criar.** Criou-se no ambiente novo um DocType no padrão real da produção (`custom=1`, módulo `Custom`), inseriu-se um registro de negócio, e então promoveu-se a DocType a "de app" (`custom=0`, módulo `Locacao Automation`) **sem** arquivo/controller correspondente no repositório:

**Veredito, com a precisão que a T1 e a T2 precisam:**

1. **O risco é real e agora está provado, não inferido.** Um DocType com `custom=0` cujo controller não importa é **apagado** pelo `bench migrate`, silenciosamente exceto por uma linha de `print`. Aplicar `custom=0` aos 18 DocTypes de negócio da produção sem entregar, no mesmo commit, o `.json` **e** o módulo `.py` do controller de cada um faz o migrate seguinte apagar todos.
2. **Mas o dano tem uma forma específica**: o que é excluído é a **definição** (`tabDocType`, campos, permissões, tudo que depende dela) — a **tabela física e os registros permanecem** (`tabCadastro Sem Arquivo` sobreviveu com a linha intacta). O docstring do Frappe ("non-destructive") é literalmente verdade quanto às linhas e enganoso quanto ao efeito: sem DocType não há list view, API `resource/`, controller, permissão nem relatório — o cadastro some para todo efeito prático, e os dados viram uma tabela órfã sem esquema declarado.
3. **`Conjunto` é a contraprova positiva**: mesmo migrate, mesmo `custom=0`, **não** foi tocado — porque a T1 entregou `conjunto.json` **e** `conjunto.py`. É exatamente o par que o `remove_orphan_doctypes` exige, e é o contrato que a T2 tem de cumprir para cada um dos 14.
4. **O critério de órfão é mais estreito do que `custom=0`, e a diferença decide o plano da T2.** A exclusão exige `ImportError` **especificamente** — o `except Exception: continue` engole todo o resto. A produção fornece o contraexemplo pronto: existem hoje **2 DocTypes `custom=0` sem controller que o migrate NÃO apagaria** (`INATIVO` e `INATIVO_2`, módulo `Locação de imóveis`, tabelas vazias). Já `Locacao Automation` **está** no `modules.txt` do app: resolve, o import é tentado de verdade, e a falta do controller vira `ImportError`.

   **PREDICADO COMPLETO — a formulação anterior desta seção estava sub-especificada.** A primeira redação dizia "controller ausente", generalizando a partir do **único** caminho que o experimento exercitou. O predicado real é:

   > um DocType é apagado ⟺ **`custom=0`** **E** **não coberto por `override_doctype_class`** **E** **`get_controller()` levanta `ImportError`**

   E `get_controller()` levanta `ImportError` por **quatro** caminhos distintos, não um. Fonte, `frappe/model/base_document.py` (`import_controller`) e `frappe/modules/utils.py` (`load_doctype_module`):

   | # | Caminho | Onde nasce | Exercitado? |
   |---|---|---|---|
   | (a) | **módulo do controller ausente** | `load_doctype_module` reembala: `except ImportError as e: raise ImportError(msg) from e` | ✅ 7.A.7 (o `Cadastro Sem Arquivo`) |
   | (b) | módulo presente, mas com **import interno que falha** | mesmo reembalo — `ModuleNotFoundError` **é** subclasse de `ImportError` | ❌ não exercitado aqui |
   | (c) | módulo importa limpo, mas **sem classe com o nome exato** | `base_document.py:99` — `getattr(module, classname, None) is None` → `raise ImportError` | ❌ não exercitado aqui |

### 7.A.13 — "A estrutura vem do repositório": decisão tomada, não alternativa aberta

O bind mount aponta para o **working tree** (`/opt/frappe/app-sync/locacao_automation`), não para um checkout de um commit. No momento desta execução, `conjunto.json` estava *staged mas não commitado*. Para o propósito desta entrega parcial a afirmação continua honesta — o `:ro` garante que o ambiente destrutível não escreve na fonte, e §7.A.6 prova que o `modified` importado é byte a byte o do arquivo —, mas ela só sustenta "reconstrói a partir do **working tree**".

A primeira redação desta seção ofereceu duas saídas como se fossem equivalentes. **Não são**, e a ADR-0002 já decidiu entre elas. O Context da ADR diz, literalmente, que o problema é «um ambiente novo criado a partir do repositório não reproduz o sistema».

- ❌ **(a) Reenunciar o critério como "reconstrói a partir do working tree" — REJEITADA.** Fecharia o AC-1 provando reconstrução **a partir do disco de quem rodou**, que é uma reformulação do problema que a ADR-0002 existe para resolver, não uma prova contra ele.
- ✅ **(b) Apontar o mount para um checkout limpo — DECISÃO.** É o que torna o `CT-028` uma prova de reprodutibilidade a partir do **repositório**.

A origem do mount foi **parametrizada** para que (b) custe uma linha (`APP_SRC`, com default relativo ao próprio arquivo de composição — o que também desamarra o compose de `/opt/frappe` e o faz funcionar em qualquer clone ou worktree):

```
git worktree add /tmp/verif-src <commit>
docker compose -f deploy/compose/docker-compose.stack-nova.yaml down -v      # <- OBRIGATORIO
APP_SRC=/tmp/verif-src/app-sync/locacao_automation \
  docker compose -f deploy/compose/docker-compose.stack-nova.yaml up -d
```

> **O `down -v` não é opcional, e a primeira versão deste procedimento o omitia.** Sem ele o passo é **no-op silencioso**: o marcador `.provisionado` vive no volume `sites`, que sobrevive ao `up -d`, então o `create-site` recriado acha o marcador, sai 0, e o site continua sendo o construído a partir do working tree — o AC-1 fecharia contra exatamente o defeito que esta seção rejeita. Medido nos dois caminhos em **§7.A.17**.

### 7.A.15 — A guarda de idempotência do `create-site` (rodada 4)

A guarda da rodada 3 era `if [ -f sites/verificacao/site_config.json ]`. **Sentinela escrita cedo demais**, e a ordem interna do bench é a prova. Verificado na fonte, `apps/frappe/frappe/installer.py`:

```python
def install_db(...):
    ...
    make_conf(db_name, site_config=site_config, ...)     # <- grava o site_config.json AQUI
    ...

def _new_site(...):
    ...
    with filelock("bench_new_site", timeout=1):
        install_db(...)                                   # <- ja gravou a sentinela
        apps_to_install = ["frappe"] + ... + list(install_apps)
        for app in apps_to_install:
            install_app(app, ...)                         # <- ERPNext instala DEPOIS (~4 min)

Consequência: o `site_config.json` existe durante **toda** a etapa mais longa e mais sujeita a falha. ### 7.A.16 — O portão virou arquivo versionado (rodada 5)

**Causa-raiz, e é a mais importante deste run inteiro: o artefato que carregava a verificação divergiu do artefato verificado.** Eu executei o portão dentro de um heredoc que tinha os imports, e publiquei na §7.A.7 o corpo do laço **sem eles**. ### 7.A.19 — `bench run-tests` sai 0 com a suíte vermelha (rodada 6)

O bloco USO publicava `bench --site verificacao run-tests --app locacao_automation` como a forma canônica de rodar a suíte aqui — e a ADR-0006 faz deste ambiente o destino dela. **Essa invocação é incapaz de sinalizar falha por código de saída.** Medido:

```
$ ... exec -T backend bench --site verificacao run-tests --module locacao_automation.tests.test_patch_criar_papel_servico_app
Ran 15 tests in 83.509s
FAILED (failures=9, errors=97)
EXIT do bench = 0

$ # em qual fluxo o placar sai?
linhas em STDOUT: 0
linhas de placar em STDERR: 2
```

É comportamento do `bench` (upstream), não deste artefato, e a §7.A.10 lê o placar **textualmente** e conclui corretamente — nada que esta task afirma está errado por causa disso. O risco é herdado por quem automatizar: T2 comparando placares, T3, CI futura.

**A primeira tentativa de correção estava travada em exit 1**, e foi medida só do lado vermelho — o único lado em que "propaga o veredito" e "nunca casa nada" são indistinguíveis. O placar sai em **stderr** e o stdout do `bench run-tests` sai **vazio**; sem `2>&1` o pipe carrega fluxo vazio, o `grep` nunca casa, e o embrulho reporta falha **inclusive com a suíte verde** — o que convidaria a removê-lo e voltar ao exit-0-sempre.

**Correção, medida nos dois lados** (lado verde emulado com o placar `OK` em stderr, sem depender da suíte ficar verde):

```
forma publicada     `... run-tests | tee /dev/stderr | grep -qE '^OK'`
  EXIT_PUBLICADA_VERMELHO=1
  EXIT_PUBLICADA_VERDE=1          <- constante 1: nunca pode reportar sucesso

2a tentativa        `... run-tests 2>&1 | tee /dev/stderr | grep -qE '^OK($| \()'`
  EXIT_2A_VERDE=0
  EXIT_2A_VERMELHO=1              <- propaga, MAS ver abaixo: abriu dois falsos-verdes
```

**A 2ª tentativa trocou um defeito por outro.** Ao ganhar a capacidade de reportar sucesso, o predicado passou a casar **qualquer linha do fluxo mesclado pelo `2>&1`**, sem âncora no placar. Dois falsos-verdes medidos:

- **Suíte com ZERO testes.** No Python **do contêiner** um `TestSuite` vazio é sucesso — verde por não ter rodado, a mesma classe de defeito que tornou `PORTAO_ESPERADO_ALVOS_MIN` obrigatória duas linhas acima. Detalhe de método que decide o achado: o comportamento **difere por versão de Python**, e o que vale é o do contêiner.

```
$ contentor (3.11.6): TextTestRunner sobre TestSuite() vazio
wasSuccessful: True
'\n---...---\nRan 0 tests in 0.000s\n\nOK\n'          <- casa `^OK`

$ host (3.12.3), para contraste
wasSuccessful: True
'\n---...---\nRan 0 tests in 0.000s\n\nNO TESTS RAN\n'
```

- **Linha espúria.** Uma suíte **vermelha** com qualquer linha igual a `OK` no fluxo (print de app, hook `before_tests`) passava — e o fluxo só está mesclado por causa do `2>&1` que a própria correção introduziu.

**Correção final: o predicado saiu do comentário e virou `deploy/scripts/veredito_suite.sh`** — três condições ancoradas no placar, não uma: (a) `^Ran [1-9][0-9]* tests?`, (b) `^OK($| \()` **exatamente uma vez**, (c) nenhum placar de falha no fluxo **bruto** — `grep -aE 'FAILED \(|^FAILED|NO TESTS RAN'` via here-string, nunca pipe (pipe + `grep -q` + `pipefail` mediu SIGPIPE como "não casou"). As duas primeiras alternativas de `FAILED` convivem porque cada uma cobre o que a outra perde: a literal `FAILED \(` fecha o escape de prefixo, e a ancorada `^FAILED` preserva a cobertura de `FAILED` sem parênteses que o predicado anterior tinha; não há âncora de fronteira (uma classe tipo `[^[:alnum:]]` dependeria do locale). O código de saída do grep é tratado em três ramos — `rc==0` reprova (achou placar de falha), `rc==1` segue (não achou) e `rc>1` reprova por inconclusão — e nunca é descartado com `|| true`, que faria a condição falhar aberta. É **conservador por construção**: fluxo sem placar, placar ambíguo ou múltiplos `OK` ⇒ VERMELHO. Um falso-vermelho custa uma investigação; um falso-verde libera migração que apaga dados.

Virou arquivo por dois motivos: três condições não cabem em comentário de YAML, e mantê-las sincronizadas em três lugares é o mecanismo que produziu os dois defeitos anteriores.

```
$ printf 'Ran 169 tests in 143.925s\nOK\n'                    | veredito_suite.sh
SUITE_VEREDITO: VERDE — Ran 169 tests in 143.925s      EXIT=0
$ printf 'Ran 169 ...\nFAILED (failures=9, errors=161, ...)\n' | veredito_suite.sh
SUITE_VEREDITO: VERMELHO — placar de falha presente    EXIT=1
$ printf 'Ran 0 tests in 0.000s\nOK\n'                        | veredito_suite.sh
SUITE_VEREDITO: VERMELHO — nenhuma execucao com contagem >= 1  EXIT=1
$ printf 'OK\nblah do app\nRan 169 ...\nFAILED (...)\n'        | veredito_suite.sh
SUITE_VEREDITO: VERMELHO — placar de falha presente    EXIT=1
$ printf 'NO TESTS RAN\n'                                      | ...  EXIT=1
$ printf ''                                                    | ...  EXIT=1  (fluxo sem placar)
$ printf 'Ran 169 ...\nOK (skipped=1)\n'                       | ...  EXIT=0  (contadores aceitos)
$ printf 'OK\nRan 169 ...\nOK\n'                               | ...  EXIT=1  (2 OK -> conservador)
```

Ponta a ponta, com a suíte real vermelha:

```

EXIT_PIPELINE=1
```

A garantia publicada passou a ser **«exit 0 só quando a suíte rodou ao menos 1 teste E passou»** — nas três ocorrências (compose e as duas aqui).

**E este é o ponto mais transferível da task.** Na mesma rodada em que eu dei ao portão veredito por código de saída (0/1/2), o comando irmão — publicado **duas linhas acima, no mesmo bloco do mesmo arquivo** — reportava sucesso em cima de vermelho, e eu não olhei.

### 7.A.20 — Fechamento do aviso de padrão

Oito variações do **mesmo** defeito de método apareceram nesta task, e nenhuma foi de conhecimento — em todas eu já tinha a informação certa registrada em algum lugar:

| # | Onde estava certo | Onde estava errado | Gate |
|---|---|---|---|
| 1 | §7.A.8b: «o isolamento vem da disjunção de bridges» | cabeçalho do compose justificava a senha por «só alcançável via `docker compose exec`» | QA MED-001 |

**O padrão não é "errei"; é "corrigi num lugar e não varri os vizinhos".** Cada correção foi tratada como pontual quando o defeito era de classe: o mesmo fato aparecia em 2+ artefatos e só um era atualizado. A mudança de classe fechou **uma** superfície: o portão deixou de ser texto e virou arquivo executado por stdin (não existe mais "a cópia publicada"), e a asserção `RODADA_INVALIDA` passou a exigir que o portão **prove que rodou** antes de poder dizer verde. **As demais superfícies continuam abertas** — as linhas 7 e 8 aconteceram *depois* da linha 5, no mesmo mecanismo (o embrulho do `run-tests`), e mesmo com o predicado agora em arquivo (`veredito_suite.sh`, §7.A.19), a garantia de propagar o veredito continua dependendo de quem invocar o script corretamente — com `2>&1` e sem descartar o código de saída. O arquivo elimina a divergência entre publicado e executado (a mesma classe de correção da linha 4), mas não elimina o erro de invocação de quem consome (T2, CI futura). Fechar essa segunda superfície é trabalho de quem herdar este artefato, não algo que esta task resolveu.

O que fica como regra prática para as tasks seguintes: **ao corrigir uma afirmação, greppar o fato corrigido em todos os artefatos da task antes de fechar** — e, quando o mesmo fato precisa viver em dois lugares, preferir eliminar um dos dois a mantê-los sincronizados na mão.
