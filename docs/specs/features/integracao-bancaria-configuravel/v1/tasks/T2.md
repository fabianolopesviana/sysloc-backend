## 2. Objetivo da Task
Extrair metadados de um PKCS#12 via `cryptography` (titular, documento ICP-Brasil, validade, emissor, impressão digital SHA-256) e materializar o certificado num arquivo temporário `0600` removido no `finally`, inclusive em erro.

---

## 3. Descrição Detalhada
Criar `cobranca_bancaria/certificado.py` (pode importar `frappe` para erros de negócio, mas a extração é `cryptography` puro):

- `ler_metadados_pfx(conteudo: bytes, senha: str) -> CertificadoDigital` via `cryptography.hazmat.primitives.serialization.pkcs12.load_key_and_certificates`. Extrai: titular (CN), documento (padrão ICP-Brasil — `CN = "NOME:CPFCNPJ"` e/ou `otherName` OIDs `2.16.76.1.3.1`/`2.16.76.1.3.4`), `not_valid_before`/`not_valid_after`, emissor, fingerprint SHA-256 do DER. Senha errada / não-PKCS#12 / tamanho fora da faixa ⇒ erro de negócio (`CERTIFICADO_INVALIDO`), **nunca** stacktrace de `cryptography`.
- `materializar_certificado(credenciais)` — context manager: cria `tempfile.NamedTemporaryFile(delete=False)`, aplica `os.chmod(0o600)` **antes** de escrever o conteúdo, entrega o path e **remove no `finally`** inclusive quando o bloco lança.
- Cálculo de `dias_para_vencer` recebendo a data de referência como parâmetro (testável nas bordas, sem relógio global).
- Criar `tests/fixtures_certificado.py` — gera PKCS#12 de teste com `cryptography` (par de chaves + certificado autoassinado com CN no padrão ICP-Brasil).

A faixa de tamanho aceitável é ponto em aberto (§21); usar constante nomeada com placeholder documentado até a definição.

### 6.6 Detalhamento dos Casos de Teste

#### CT-004 — Extração de metadados de certificado PKCS12 válido (titular, documento, validade, emissor, fingerprint)
- **Tipo/Camada**: UNITARIO · unit · CA CA-04, CA-11
- **Invariante**: Dado um arquivo PKCS12 válido e a senha correta, a extração de metadados retorna titular (CN), documento (CPF/CNPJ do padrão ICP-Brasil quando presente no CN), data de início e fim de validade, emissor e fingerprint SHA-256 — todos derivados do certificado, nunca da senha ou do conteúdo bruto.
- **Pré-condições**: Um .pfx de teste autoassinado gerado em memória com a biblioteca `cryptography` no setUp (CN, validade e senha conhecidos), sem depender de arquivo externo versionado
- **Entrada**: {"descricao": "Bytes do PKCS12 de teste + senha correta", "valores": {"senha": "senha-de-teste-123", "cn_esperado": "TITULAR TESTE LTDA", "validade_dias": 365}}
- **Passos**: Gerar em memória (setUp) um certificado autoassinado + chave, empacotar em PKCS12 com senha conhecida usando `cryptography`.; Chamar a função de extração de metadados com os bytes do PKCS12 e a senha.; Calcular independentemente o SHA-256 esperado do certificado DER para comparação.
- **Esperado**: "Metadados retornados: titular == CN usado na geração; validade_inicio/validade_fim batem com o certificado gerado; fingerprint SHA-256 retornado == SHA-256 calculado independentemente pelo teste sobre os bytes DER do certificado (não sobre o PKCS12 inteiro nem sobre a senha)."
- **Negative companion**: CT-005 — arquivo corrompido / não-PKCS12 → erro de negócio claro, nenhum metadado parcial retornado
- **Execução real**: none (fronteira HTTP mockada — provedor não é chamado)

#### CT-005 — Extração de metadados falha com erro de negócio claro para certificado corrompido ou não-PKCS12
- **Tipo/Camada**: UNITARIO · unit · CA CA-03
- **Invariante**: Bytes que não formam um PKCS12 válido (arquivo truncado, texto arbitrário, PDF renomeado) nunca produzem metadados parciais — sempre um erro de negócio explícito.
- **Pré-condições**: Bytes de PDF válido reaproveitados de fixture (ex.: cabeçalho %PDF) e bytes truncados de um PKCS12 real gerado em setUp
- **Entrada**: {"descricao": "Dois cenários parametrizados de entrada inválida", "valores": {"casos": ["bytes_de_pdf_renomeado", "pkcs12_truncado_50_por_cento"]}}
- **Passos**: Para cada bytes inválido, chamar a função de extração de metadados com uma senha qualquer.
- **Esperado**: "Para ambos os casos: erro de negócio explícito é levantado/retornado (não uma exceção crua de `cryptography`), e nenhum metadado (titular/validade/fingerprint) é produzido."
- **Negative companion**: self — bytes de um PDF válido renomeado para .pfx; bytes truncados de um PKCS12 real → erro de negócio ('certificado inválido' ou equivalente) sem vazar traceback técnico da lib cryptography; nenhum dict de metadados é retornado
- **Execução real**: none (fronteira HTTP mockada — provedor não é chamado)

#### CT-006 — Certificado recusado por senha incorreta, formato inválido ou tamanho fora da faixa aceitável
- **Tipo/Camada**: UNITARIO · unit · CA CA-03
- **Invariante**: RN-05: um certificado só é aceito se abrir com a senha informada e estiver dentro da faixa de tamanho aceitável; qualquer uma dessas violações recusa o envio sem persistir nada, com mensagem de negócio distinguível da causa.
- **Pré-condições**: PKCS12 de teste válido gerado em setUp com senha conhecida
- **Entrada**: {"descricao": "Tabela parametrizada de violações de RN-05", "valores": {"casos": [{"cenario": "senha_incorreta", "senha_usada": "senha-errada"}, {"cenario": "tamanho_abaixo_da_faixa", "tamanho_bytes": 1}, {"cenario": "tamanho_acima_da_faixa", "tamanho_bytes": "PLACEHOLDER_LIMITE_SUPERIOR+1"}]}}
- **Passos**: Para 'senha_incorreta': chamar a validação com o PKCS12 válido e senha errada.; Para os cenários de tamanho: chamar a validação com bytes cujo tamanho está fora da faixa aceitável (placeholder até faixa ser definida).
- **Esperado**: "Todos os 3 cenários retornam recusa (não exceção não tratada) com mensagem de negócio identificando a causa; nenhuma chamada de persistência é feita nesta camada (função pura de validação)."
- **Negative companion**: self — senha errada num PKCS12 válido; arquivo 1 byte maior/menor que a faixa aceitável → erro de negócio específico por causa (senha_incorreta vs tamanho_invalido), nunca uma exceção genérica
- **Execução real**: none (fronteira HTTP mockada — provedor não é chamado)

#### CT-007 — Cálculo de dias restantes até o vencimento do certificado nas fronteiras (vencido, vence hoje, vence no futuro)
- **Tipo/Camada**: UNITARIO · unit · CA CA-11, CA-15
- **Invariante**: O cálculo de dias restantes para o vencimento do certificado é consistente com a data de referência: negativo/zero quando já vencido ou vence hoje, positivo quando no futuro — nunca lança exceção para nenhuma das três fronteiras.
- **Pré-condições**: Data de referência ('hoje') injetada explicitamente na função, não lida de `datetime.now()` direto, para determinismo do teste
- **Entrada**: {"descricao": "Tabela parametrizada de datas de validade vs. data de referência fixa 2026-07-20", "valores": {"casos": [{"data_validade": "2026-07-19", "esperado_dias": -1, "esperado_vencido": true}, {"data_validade": "2026-07-20", "esperado_dias": 0, "esperado_vencido": true}, {"data_validade": "2026-08-19", "esperado_dias": 30, "esperado_vencido": false}]}}
- **Passos**: Para cada linha, chamar a função de cálculo com data_validade e data_referencia=2026-07-20 injetada.
- **Esperado**: "dias_restantes e vencido batem exatamente com esperado_dias/esperado_vencido de cada linha."
- **Negative companion**: self — data_validade no passado (certificado já vencido) → retorna valor <= 0, nunca exceção, e um indicador de 'vencido' == True
- **Execução real**: clock (fronteira HTTP mockada — provedor não é chamado)

#### CT-013 — Certificado materializado em arquivo temporário 0600 é removido no finally mesmo quando a chamada ao provedor falha
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-16
- **Invariante**: D4: o material do certificado materializado em disco para uma operação é sempre removido ao final dela, inclusive quando a chamada HTTP ao provedor lança exceção — nunca fica órfão em disco, e enquanto existe tem permissão restrita ao proprietário (0600).
- **Pré-condições**: Configuração ativa com certificado válido armazenado como conteúdo no banco (não mais caminho fixo em disco)
- **Entrada**: {"descricao": "2 cenários: chamada ao provedor bem-sucedida vs. lança exceção", "valores": {"casos": ["sucesso", "excecao_de_rede"]}}
- **Passos**: Interceptar (spy) a função de materialização para capturar o caminho do arquivo temporário criado.; Mockar a chamada HTTP do adaptador (`requests_pkcs12.post`) para o cenário: sucesso normal, ou lançar `RequestException`.; Executar a operação completa (ex.: emissão) através do serviço.; Verificar, após a operação retornar (sucesso ou erro), se o caminho capturado ainda existe no filesystem e quais
- **Esperado**: "Em AMBOS os cenários: `os.path.exists(caminho_temp) == False` após a operação retornar; durante a existência do arquivo (capturada via monkeypatch no ponto de criação), o modo de permissão era 0o600."
- **Negative companion**: self — chamada HTTP ao provedor mockada para lançar `RequestException` → arquivo temporário não existe mais no filesystem após a operação, mesmo tendo lançado exceção no meio
- **Execução real**: filesystem (fronteira HTTP mockada — provedor não é chamado)
