## 2. Objetivo da Task
Adicionar os métodos de gestão do certificado (envio validado com extração de metadados, remoção) e o registro de auditoria sanitizado das trocas.

---

## 3. Descrição Detalhada
Adicionar a `integracao_bancaria_api/service.py` e criar `integracao_bancaria_api/auditoria.py`:

- `enviar_certificado({arquivo_base64, nome_arquivo, senha})` — decodifica (validate=True), valida faixa de tamanho, chama `ler_metadados_pfx`; falha → erro de negócio, **nada gravado** (CT-012). Sucesso → grava File privado (`is_private=1`) no registro **pendente**, campos read-only derivados, e chama `registrar_alteracao`. Retorna bloco `certificado`, sem senha/bytes.
- `remover_certificado` — apaga o File privado do pendente e limpa os metadados derivados; sem certificado próprio → erro de negócio (CT-021).
- `auditoria.registrar_alteracao(...)` — grava autor (`frappe.session.user`), data, ação, impressões digitais anterior/nova, `campos_alterados` (só nomes), resultado, mensagem sanitizada. **Nunca** senha, bytes ou valores de campo (RN-06, CT-009).

Este módulo compartilha `service.py` com T11 (arquivo de alta contenção) → sequencial dentro da Fase 4.

### 6.6 Detalhamento dos Casos de Teste

#### CT-009 — Sigilo: serialização de evento de auditoria nunca inclui senha nem bytes do certificado
- **Tipo/Camada**: UNITARIO · unit · CA CA-01, CA-14
- **Invariante**: RN-06: para qualquer payload de entrada/configuração serializado num registro de evento ou de auditoria, os campos de senha e o conteúdo binário do certificado são sempre removidos/mascarados antes da serialização — nunca aparecem no JSON resultante, mesmo que estivessem presentes no dict original.
- **Pré-condições**: Função de sanitização de payload para registro de evento/auditoria implementada
- **Entrada**: {"descricao": "Dict de configuração completo incluindo campos sensíveis", "valores": {"payload": {"client_id": "abc123", "pfx_password": "SENHA_SECRETA_XYZ", "pfx_base64": "TW9ja1BLQ1MxMkJ5dGVz", "numero_conta_corrente": "12345"}}}
- **Passos**: Chamar a função de sanitização/serialização com o payload contendo os campos sensíveis.; Buscar as substrings literais 'SENHA_SECRETA_XYZ' e 'TW9ja1BLQ1MxMkJ5dGVz' no texto JSON resultante inteiro.
- **Esperado**: "Nenhuma das duas substrings sensíveis aparece em nenhum ponto do JSON serializado; campos não-sensíveis (client_id, numero_conta_corrente) permanecem presentes e corretos."
- **Negative companion**: self — payload contendo chaves 'pfx_password', 'pfx_base64' e 'senha' com valores reais → o JSON serializado não contém as strings dos valores originais em nenhuma posição (busca substring no texto serializado inteiro, não só nas chaves esp
- **Execução real**: none (fronteira HTTP mockada — provedor não é chamado)

#### CT-012 — Certificado com senha incorreta é recusado e nada é gravado na configuração (observável em banco)
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-03
- **Invariante**: RN-05: quando o envio de certificado é recusado por senha incorreta, a configuração ativa permanece byte-a-byte inalterada no banco — nenhum campo (fingerprint, titular, caminho do arquivo) é atualizado.
- **Pré-condições**: Configuração ativa pré-existente com um certificado válido já registrado (fingerprint/titular conhecidos)
- **Entrada**: {"descricao": "Novo PKCS12 válido com senha incorreta informada", "valores": {"senha_informada": "senha-errada-999"}}
- **Passos**: Capturar snapshot completo da configuração ativa antes da tentativa (todos os campos + fingerprint).; Chamar o serviço de envio de certificado com senha incorreta.; Recarregar a configuração do banco (nova query, não do cache do objeto em memória) e comparar com o snapshot.
- **Esperado**: "Serviço retorna {success: False, message: <negócio>}; a configuração recarregada do banco é campo-a-campo idêntica ao snapshot (fingerprint, titular, caminho do arquivo inalterados)."
- **Negative companion**: CT-016 — n/a — este é o caso negativo de CT-016 (CA-02) → config em banco idêntica ao snapshot pré-tentativa (comparação campo a campo)
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-016 — CA-02: envio de certificado válido com senha correta é aceito e passa a ser a credencial da configuração
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-02, CA-04
- **Invariante**: CA-02: um certificado válido enviado com a senha correta é aceito e a configuração passa a apresentá-lo (fingerprint, titular, validade) como a credencial em uso, persistido no banco.
- **Pré-condições**: Configuração ativa pré-existente sem certificado próprio (usando fallback legado)
- **Entrada**: {"descricao": "PKCS12 válido gerado em setUp + senha correta", "valores": {"senha": "senha-de-teste-123"}}
- **Passos**: Chamar o serviço de envio de certificado com o PKCS12 válido e a senha correta.; Recarregar a configuração do banco.
- **Esperado**: "Serviço retorna {success: True, ...}; a configuração recarregada do banco tem fingerprint/titular/validade preenchidos batendo com o certificado enviado."
- **Negative companion**: CT-012 — mesmo certificado, senha incorreta → ver CT-012 — nada é gravado
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-021 — CA-12: remoção do certificado apaga a credencial e as informações derivadas; remoção sem certificado próprio é recusada
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-12
- **Invariante**: CA-12: solicitar a remoção de um certificado enviado pela tela apaga a credencial materializada e todas as informações dela derivadas (fingerprint, titular, validade), deixando a configuração sem certificado próprio; solicitar remoção quando não há certificado próprio enviado é recusado com erro de negócio, preservando o fallback legado intacto.
- **Pré-condições**: Configuração ativa com certificado próprio enviado (fingerprint/titular/validade preenchidos e arquivo privado real existente)
- **Entrada**: {"descricao": "2 cenários: config com certificado próprio vs. config só com fallback legado", "valores": {"casos": ["com_certificado_proprio", "somente_fallback_legado"]}}
- **Passos**: Cenário 1: chamar o serviço de remoção sobre uma config com certificado próprio.; Recarregar a config do banco e verificar campos derivados e existência do arquivo privado.; Cenário 2: chamar o serviço de remoção sobre uma config sem certificado próprio (só fallback).
- **Esperado**: "Cenário 1: fingerprint/titular/validade == None/vazio na config recarregada; arquivo privado do certificado não existe mais. Cenário 2: erro de negócio explícito, nenhuma mudança de estado."
- **Negative companion**: self — remoção solicitada quando a configuração nunca teve certificado próprio (apenas fallback legado) → erro de negócio explícito; nenhuma alteração no fallback legado
- **Execução real**: filesystem (fronteira HTTP mockada — provedor não é chamado)

#### CT-023 — CA-14/RN-12: toda alteração de configuração registra autor, data e identificação do certificado anterior e do novo
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-14
- **Invariante**: RN-12: toda troca de certificado gera exatamente um registro de auditoria contendo autor (usuário autenticado que executou a ação), data/hora, e a identificação (fingerprint) do certificado anterior e do novo — nunca senha ou bytes do certificado (RN-06); uma tentativa recusada (ex.: teste de conexão falho) não deve gerar um registro de 'em vigor'.
- **Pré-condições**: Configuração ativa com certificado A (fingerprint conhecido); usuário de teste autenticado como administrador via `frappe.set_user`
- **Entrada**: {"descricao": "Troca bem-sucedida de A para certificado B", "valores": {"usuario_autor": "admin-teste@example.com"}}
- **Passos**: Definir `frappe.session.user` para o usuário de teste administrador.; Executar a troca completa de certificado (envio + teste de conexão mockado com sucesso + confirmação).; Consultar no banco o(s) registro(s) de auditoria criados para essa troca.
- **Esperado**: "Exatamente 1 registro de auditoria com autor == 'admin-teste@example.com', data/hora preenchida, fingerprint_anterior == fingerprint de A, fingerprint_novo == fingerprint de B; nenhum campo de senha/bytes presente no registro."
- **Negative companion**: self — troca de certificado que falha no teste de conexão (RN-04) antes de entrar em vigor → nenhum registro de auditoria de 'configuração alterada/em vigor' é criado para essa tentativa
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)
