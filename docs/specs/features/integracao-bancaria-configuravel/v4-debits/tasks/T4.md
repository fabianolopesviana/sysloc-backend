## 4. Detalhes de Implementação

### 4.1 Contexto do Débito

**Origem**: task `T1` da `v3` — Gate 2 (Tech Review).

O helper deleta os `File` próprios cuja `file_url` diverge de `url_alvo` e **só depois** insere o vínculo do alvo. As duas etapas não são simétricas em transacionalidade: `frappe.delete_doc` remove o binário do disco imediatamente (`on_trash` → `_delete_file_on_disk`), enquanto o rollback do Frappe restaura apenas a **linha** do `File`.

Dois modos de falha, ambos com `url_alvo` inválida:

- **(a)** binário do alvo ausente no disco → `validate_file_on_disk` lança `IOError`, a transação aborta e a linha do `File` obsoleto volta apontando para um binário **já apagado do disco**.
- **(b)** `url_alvo` com prefixo público (`/files/...`, justamente o resíduo do incidente) → `validate_file_path` lança `ValidationError`. A operação falha alto — **não há downgrade silencioso para público**, o que confirma a promessa de "divergência explícita" —, mas o erro sobe como exceção técnica do Frappe, não como `_falha(...)` de negócio, travando as 4 operações de configuração até intervenção manual.

**Restrição estrutural**: a ordem delete-antes-de-insert **não pode ser simplesmente invertida** — `validate_duplicate_entry`/dedup por hash reapontariam o vínculo novo para a url obsoleta. Por isso a correção é **pré-validar**, não reordenar.

**Alcançabilidade**: exige `certificado_arquivo` já corrompido no banco. A url vem sempre de campos internos (`ativo.get(...)` ou do próprio pendente), nunca de input direto do usuário.

**Categoria**: `error_handling` (BAIXO) · **Custo**: ~60min · **Risco de regressão**: `medio`

> **Incluído por decisão explícita do usuário**, ciente de que o especialista o classificou como **perfumaria com risco médio** — é o único débito desta versão que altera runtime, na mesma função que causou o incidente de produção e custou 3 tentativas na v3.

### 4.2 Correção

- [x] No início de `_replicar_vinculo_certificado`, após normalizar `url_alvo`: se não vazia e **não** começar com `/private/files/`, abortar com erro de negócio explícito **antes** de apagar qualquer `File`.
- [x] Verificar a existência do binário do alvo (mesmo critério de `validate_file_on_disk`) antes das deleções, devolvendo erro de negócio se ausente.
- [x] Preservar o caminho feliz **bit-a-bit**: mesma ordem de operações, mesmo resultado, para toda `url_alvo` válida.
- [x] Preservar o comportamento de `url_alvo` vazia (limpa o campo e retorna) exatamente como está hoje.

### CT-036 — `url_alvo` inválida é recusada antes de destruir estado

- **Invariante**: com `url_alvo` inválida (prefixo público ou binário ausente), o helper devolve **erro de negócio** e **nenhum `File` é apagado** — o estado anterior permanece intacto.
- **Asserção literal**: os `File` próprios do documento antes e depois são os **mesmos** (por `name`); o retorno é o erro de negócio esperado, não exceção técnica do Frappe.
- **Negative companion**: com `url_alvo` **válida**, o caminho feliz continua idêntico — vínculo criado, `is_private = 1`, mesma `file_url`.
