## 2. Objetivo da Task
Apurar os boletos em aberto (RN-02), montar o PDF consolidado em memória com os disponíveis (listando os ausentes) e expô-lo por um endpoint de streaming dedicado, restrito a System Manager.

---

## 3. Descrição Detalhada
Criar `integracao_bancaria_api/boletos_abertos.py` e adicionar o endpoint a `service.py`:

- `listar_boletos_abertos()` — filtro canônico de RN-02 (`status_cobranca in [Pendente, Vencida]`, `boleto_gerado=1`, `nosso_numero` preenchido), já usado em `rotina_pagamentos.py`. Devolve contagem e identificadores.
- `montar_pdf_consolidado()` — compõe em memória com `pypdf` (`PdfReader`/`PdfWriter`) os boletos com PDF disponível (`obter_pdf_privado_bytes`); retorna os bytes + a lista de ausentes (RN-09, CT-020). Não persiste (D6).
- `baixar_consolidado_boletos_abertos()` — `@frappe.whitelist()` restrito a System Manager; entrega por `frappe.local.response` (padrão `abrir_boleto`, sem `return`). É o único método de API que devolve arquivo em vez de JSON. **Não** é `allow_guest` (expõe a carteira inteira).

A confirmação de troca com três opções vive em `salvar_configuracao` (T11); esta task fornece o consolidado que a terceira opção aciona antes da troca.

### 6.6 Detalhamento dos Casos de Teste

#### CT-019 — CA-08: boletos em aberto emitidos pela conta atual apresentam contagem e as três opções de decisão
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-08
- **Invariante**: RN-08: havendo boletos em aberto emitidos pela conta atual, a troca de configuração exige uma das três decisões explícitas do gestor (aceitar / não aceitar / aceitar com consolidado); cada caminho produz um efeito diferente e mutuamente exclusivo sobre a configuração.
- **Pré-condições**: 3 registros de Cobranca no banco de teste com status_cobranca in ('Pendente','Vencida'), boleto_gerado=1, nosso_numero preenchido, vinculados à conta atual (reproduzindo o filtro de rotina_pagamentos.py:36-40)
- **Entrada**: {"descricao": "3 cenários de decisão do gestor sobre a mesma troca pendente", "valores": {"casos": ["aceitar", "nao_aceitar", "aceitar_com_consolidado"]}}
- **Passos**: Confirmar que a apuração retorna quantidade == 3 boletos em aberto antes de qualquer decisão.; Para cada cenário, invocar o serviço de confirmação de troca com a decisão correspondente.; Recarregar a configuração do banco após cada decisão.
- **Esperado**: "'aceitar': troca prossegue, nova config fica ativa. 'nao_aceitar': config inalterada, troca cancelada por completo. 'aceitar_com_consolidado': troca prossegue E o documento consolidado é gerado (delegunderado a CT-020) antes de confirmar."
- **Negative companion**: self — gestor escolhe 'não aceitar' → operação cancelada por completo; configuração atual recarregada do banco permanece byte-a-byte inalterada
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-020 — CA-09/CA-10/RN-09: documento consolidado reúne boletos com PDF disponível e lista explicitamente os ausentes
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-09, CA-10
- **Invariante**: RN-09: o documento consolidado sempre reúne exatamente os boletos em aberto cujo PDF individual está disponível, e sempre informa explicitamente (por identificador) quais boletos ficaram de fora por falta de comprovante — nunca omite silenciosamente um boleto sem PDF.
- **Pré-condições**: 3 Cobranca em aberto no banco: 2 com pdf_boleto_arquivo apontando para um PDF real salvo via `salvar_pdf_privado` (arquivo privado real no filesystem de teste), 1 sem PDF disponível
- **Entrada**: {"descricao": "3 boletos em aberto, 2 com PDF real de 1 página cada, 1 sem PDF", "valores": {"boletos_com_pdf": 2, "boletos_sem_pdf": 1}}
- **Passos**: Preparar os 2 PDFs reais (1 página cada, conteúdo mínimo válido gerado com reportlab) e salvá-los como arquivo privado real via `salvar_pdf_privado`.; Chamar o serviço de montagem do documento consolidado para os 3 boletos em aberto.; Abrir o PDF consolidado resultante com pypdf e contar páginas.
- **Esperado**: "PDF consolidado real tem exatamente 2 páginas (uma por boleto com PDF disponível); a lista de ausentes retornada contém exatamente o identificador do 3º boleto (sem PDF), nunca vazia quando há ausente."
- **Negative companion**: self — nenhum dos boletos em aberto possui PDF disponível → documento consolidado é gerado vazio/mínimo e a lista de ausentes contém os 3 identificadores de boleto, nenhum se perde
- **Execução real**: filesystem (fronteira HTTP mockada — provedor não é chamado)
