## 2. Objetivo da Task
Criar o módulo de API com os três métodos whitelisted de leitura/edição/teste, no shape `{success, message, ...}`, com o ciclo de registro pendente + carimbo invalidável (RN-04) e acesso restrito a System Manager.

---

## 3. Descrição Detalhada
Criar `integracao_bancaria_api/service.py` (e `__init__.py`), todos `@frappe.whitelist()` com verificação explícita de System Manager no início (RN-11):

- `obter_configuracao` — devolve a config **ativa** sem segredos (client_id mascarado, senha nunca) + bloco `certificado` (`presente`, titular, documento, emissor, validade, `dias_para_vencer`, `origem`) + bloco `pendente` quando existir (campos divergentes + estado do carimbo).
- `salvar_configuracao` — **atualização parcial**; grava num registro **pendente** (`ativo=0`), limpa o carimbo; a senha só é gravada quando enviada não-vazia. Não ativa nada.
- `testar_conexao` — executa `adaptador.obter_token()` sobre o pendente; sucesso grava `conexao_testada_em`/`conexao_testada_hash`; a ativação só ocorre com carimbo válido correspondente ao estado atual (RN-04). Retorna `{success, mensagem, detalhes, expires_in, scope}`.

O detalhamento do ciclo pendente/ativação está na §7.2.

### 3.1 Exemplo de Payload
**salvar_configuracao — atualização parcial**. Body mínimo (só o campo mais comum):
```
{"numero_conta_corrente": 222}
```
Campos ausentes permanecem inalterados; `certificado_senha` só grava se enviada não-vazia (string vazia/ausente não apaga a existente). Nenhum campo é obrigatório no corpo — a config pendente é resolvida no servidor. Diferente de um POST de criação, onde os campos seriam obrigatórios.

#### CT-017 — CA-05: alteração dos dados da conta é considerada nas próximas emissões; alteração inválida é recusada
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-05
- **Invariante**: CA-05: alterar e confirmar os dados da conta no provedor faz a configuração passar a considerar a nova conta para as próximas cobranças; dados incompletos/inválidos são recusados sem tocar a configuração vigente.
- **Pré-condições**: Configuração ativa com numero_conta_corrente = '111'
- **Entrada**: {"descricao": "2 cenários: dados válidos ('222') vs. inválidos (vazio)", "valores": {"casos": [{"numero_conta_corrente": "222", "esperado_sucesso": true}, {"numero_conta_corrente": "", "esperado_sucesso": false}]}}

#### CT-031 — Invariante 7.2: dois ciclos consecutivos não revertem config anterior (regressão P1 Tech Review)
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-06 / RN-04
- **Invariante**: após um ciclo `salvar→testar→ativar`, o registro que sai de vigor é re-sincronizado com o novo ativo (não remanesce com valores obsoletos). Um segundo ciclo que edita SOMENTE outro campo parte sempre do ativo EM VIGOR — nunca reverte silenciosamente um campo confirmado no ciclo anterior (o pendente = ativo corrente + deltas desta sessão).
- **Pré-condições**: Configuração A ativa com `numero_conta_corrente = 111`.
- **Entrada**: dois ciclos sequenciais com `requests_pkcs12.post` mockado para sucesso — Ciclo 1: `numero_conta_corrente=222`; Ciclo 2: `api_base_url='https://sandbox.sicoob.com.br/cobranca-bancaria/v3/boletos'`.
- **Passos**: (1) `salvar_configuracao(numero_conta_corrente=222)` → `testar_conexao` (mock sucesso) → confirmar ativa=222 e ex-ativo re-sincronizado para 222/ativo=0; (2) `salvar_configuracao(api_base_url=nova_url)` → `testar_conexao` (mock sucesso); (3) recarregar do banco a única config ativa.
- **Esperado**: "Config ativa final tem `numero_conta_corrente == 222` (NÃO voltou para 111) E `api_base_url == nova_url`. Sempre exatamente uma config ativa por provedor."
- **Negative companion**: a ausência da correção reintroduziria 111 no ciclo 2 (o ex-ativo obsoleto seria reusado como base do pendente e só o delta de URL aplicado sobre valores do ciclo anterior).
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

#### CT-032 — P3: contador de runtime `ultimo_sequencial_seu_numero` não regride pela janela salvar→testar→ativar (regressão P3 Tech Review)
- **Tipo/Camada**: INTEGRACAO · service-integration · CA CA-05 / RN-04
- **Invariante**: `ultimo_sequencial_seu_numero` é um contador de RUNTIME mutado out-of-band na config ATIVA por `gerar_seu_numero` (`SELECT ... ativo=1 FOR UPDATE` + `set_value`) a cada boleto. Na ativação do pendente, o contador nunca pode regredir abaixo do valor VIVO da ativa que sai — senão os `seu_numero` já emitidos na janela seriam reutilizados (duplicidade proibida pelo Sicoob). Prova a MONOTONICIDADE REAL através da janela.
- **Pré-condições**: Config A ativa; contador fixado em `N` (500) ANTES do `salvar` (para o snapshot do pendente congelar `N`).
- **Entrada**: N=500, k=3 emissões reais na janela; `requests_pkcs12.post` mockado para sucesso no `testar_conexao`.
- **Passos**: (1) `salvar_configuracao(numero_conta_corrente=222)` cria o pendente B, que copia o contador congelado `N=500`; (2) na janela salvar→testar, chamar `gerar_seu_numero` k=3 vezes — a ATIVA A avança para N+k=503 (último emitido=503); (3) `testar_conexao` (mock sucesso) → B ativa, A desativada; (4) reler o contador da nova ativa e chamar `gerar_seu_numero` de novo.
- **Esperado**: "Contador da nova ativa (B) >= N+k (503), nunca <= N (500) — carry-forward do valor vivo com `max`, lido com FOR UPDATE. A próxima emissão produz `novo_sequencial` estritamente > o último emitido na janela (504 > 503) — nenhum seu_numero reutilizado. O ex-ativo re-sincronizado (P1) também não regride abaixo de N+k."
- **Negative companion**: sem o carry-forward, B ativaria com o snapshot congelado N=500 e a próxima emissão geraria 501, DUPLICANDO os seu_numero 501..503 já emitidos na janela.
- **Execução real**: db (fronteira HTTP mockada — provedor não é chamado)

## 7. Observações e ADRs

### Correção pós-Tech Review (Gate 2 — REJEITADO CRÍTICO)

- **P1 (architecture, CRÍTICO) — reversão silenciosa de config entre ciclos.** **Causa-raiz**: na ativação (`testar_conexao`), o registro anteriormente ativo era apenas marcado `ativo=0` e deixado no banco com os valores do ciclo anterior; `_nome_pendente` (filtra `ativo=0`) não distinguia esse ex-ativo obsoleto de um rascunho genuíno, então a edição seguinte o carregava como base e aplicava só o delta sobre valores desatualizados — campos não editados (ex.: `numero_conta_corrente`) revertiam. **Correção (Opção A adaptada — re-sincronização na ativação)**: `_ressincronizar_ex_ativo` copia integralmente o novo ativo para o ex-ativo (`ativo=0`) logo após a troca, limpando o carimbo. Assim o único pendente remanescente reflete sempre o estado EM VIGOR. Escolhida a re-sincronização em vez da DELEÇÃO literal (Opção A) porque deletar o ex-ativo (a) dispararia `LinkExistsError` na config migrada, que possui registro de `Auditoria Configuracao Bancaria` apontando para ela (RN-12 torna a auditoria indeletável), abortando a ativação em produção, e (b) quebraria a pós-condição `ativo==0` de CT-018. Também descartada a Opção C (re-sync a cada `salvar`) por reverter deltas acumulados numa sessão multi-edição (viola "campos ausentes permanecem inalterados", §3.1). Provado por **CT-031** (dois ciclos consecutivos).
- **P3 (architecture, CRÍTICO) — contador de runtime `ultimo_sequencial_seu_numero` revertia no ciclo pendente→ativação (seu_numero DUPLICADO).** **Causa-raiz**: o campo foi modelado como um campo da DocType de configuração e entrou em `CAMPOS_COPIAVEIS` junto com `auth_url`/`client_id`/conta, tratado como estado de config snapshotável no ciclo pendente. Mas, ao contrário dos demais, ele NUNCA é editado por `salvar_configuracao`: é um contador de RUNTIME incrementado out-of-band na linha `ativo=1` por `gerar_seu_numero` (`SELECT ... ativo=1 FOR UPDATE` + `set_value`) a cada boleto. Snapshotar um valor que só se move na ativa o congela no pendente; a ativação (que promove o snapshot congelado e desativa a ativa viva) descartava os incrementos ocorridos na janela `salvar→testar`, regredindo o contador de N+k para N e reabrindo os `seu_numero` N+1..N+k já emitidos — violação de integridade (Sicoob). **Correção (carry-forward do contador vivo)**: em `testar_conexao`, na ATIVAÇÃO (após o carimbo validado, na MESMA transação da troca de ativo), lê-se o valor VIVO do contador da ativa que sai com `SELECT ... WHERE name=% FOR UPDATE` (`_ler_sequencial_vivo_for_update`) — travando a MESMA linha que `gerar_seu_numero` bloqueia, para serializar contra uma emissão concorrente — e aplica-se `max(contador_pendente, contador_vivo)` (`_max_sequencial`, 12 dígitos, nunca regride) no pendente antes de flipar. O contador é MANTIDO em `CAMPOS_COPIAVEIS` de propósito (combinação coerente): (a) `_criar_pendente_de_ativa` dá ao pendente um PISO não-vazio, evitando que `_normalizar_sequencial_texto` o resete para `...0001` caso a ativação ocorra sem ativa que sai; (b) `_ressincronizar_ex_ativo` (P1) propaga o valor JÁ corrigido pelo carry-forward para o ex-ativo, reconciliando P1↔P3 (o ex-ativo re-sincronizado também nunca fica com contador menor que o vivo). O campo `ultimo_sequencial_seu_numero` NÃO faz parte de `CAMPOS_COMPONENTES_CONEXAO`, então o carry-forward não invalida o carimbo. Provado por **CT-032** (monotonicidade real através da janela, com emissões reais avançando a ativa).
- **P2 (error_handling, BAIXO) — `except Exception` amplo em `_senha_do_doc`.** **Causa-raiz**: sem `raise_exception=False`, a única forma de tolerar senha ausente/vazia era capturar tudo, engolindo erros reais sem log. **Correção**: `get_password('certificado_senha', raise_exception=False)` trata o caso esperado (retorna `None`); o `except` remanescente cobre apenas falhas reais e agora registra `frappe.log_error(...)` antes da degradação graciosa para `''`.
